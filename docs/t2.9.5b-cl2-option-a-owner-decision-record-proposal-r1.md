## 1. Exact owner decision being recorded

> **CL2 — WAV chunk order — OWNER APPROVED 2026-11-04 — OPTION A**
>
> The Project Owner approved CL2 Option A on 2026-11-04. The approved policy is:
>
> - exactly one `fmt ` chunk;
> - exactly one `data` chunk;
> - `fmt ` must immediately precede `data`;
> - reject data-first files;
> - reject intervening chunks;
> - reject duplicate or missing `fmt ` or `data` chunks;
> - reject RIFF-size mismatches;
> - reject truncated chunks; and
> - reject impermissible trailing bytes.

The approved parser rule is:

> A canonical imported WAV must contain exactly one `fmt ` chunk followed immediately by exactly one `data` chunk. The parser walks chunks by `8 + size + (size & 1)` and never reads the audio payload to validate order. A `data` chunk encountered before `fmt ` is rejected before any provider call, with a specific malformed-chunk-order error.

The 2026-11-04 date is the Project Owner's stated decision date. No separate repository artifact is claimed to independently establish that date.

**Current register effect:** r13 still records CL2 as a `Design clarification` with a required written parser rule and parser-test mapping. The owner decision is approved, but register closure remains **PENDING DOCUMENTATION** until r14 is authorized and created.

## 3. Rationale and strongest counterargument

### 3.1 Rationale recorded for the decision

Option A establishes a deterministic canonical input contract:

1. The project requires a canonical PCM WAV rather than a general RIFF reader.
2. The accepted order is explicit and can be validated in one forward pass without deferred format state.
3. A data-first file is rejected before a manager lease or provider call, avoiding reliance on unverified provider tolerance.
4. No repository evidence identifies a supported producer that requires data-first input.
5. Option B is technically feasible, but adds deferred parser state and a larger test matrix without an established additional safety property or a demonstrated producer requirement.

### 3.2 Strongest counterargument preserved

If a real supported producer emits data-first WAV files, Option A would reject a file that some readers might handle, and the owner would need a conversion step or a later policy change. Option B is technically feasible at modest cost and would make IR3 eligible for separate consideration. That argument is not sufficient without evidence that such a producer is actually in scope, and Option B would still require an explicit provider-acceptance test before any end-to-end data-first support could be claimed.

The counterargument is preserved so that the decision record does not overstate the evidence for Option A. Option A is an owner-selected canonical policy, not a requirement already explicitly stated in the source design, and the external WAVE reference is technical context rather than repository evidence.
