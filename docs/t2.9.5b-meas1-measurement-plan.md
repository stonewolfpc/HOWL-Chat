## 1. Purpose

This plan defines one measurement question and the evidence required to answer it:

> On the exact packaged application under test, can one complete production-shaped `TranscribeAudio` request carry a `WAVBase64` field of exactly **51,200,120 characters** intact through the actual generated Wails binding, JSON serialization, IPC/framing, and Go unmarshalling to the `TranscribeAudio` handler, without rejection, truncation, substitution, loss, timeout, or other failure?

The threshold is derived from the owner-approved AQ4 rule:

```text
P  = MaxBase64Chars = 25,600,060
2P = 51,200,120
T6 passes when C ≥ 2P
Equality passes
```

This plan measures a **verified lower bound** at the acceptance threshold. It does not attempt to find the exact maximum binding capacity. A successful result supports `C_verified ≥ 51,200,120`; it does not support a claim that no larger value can pass.

### 1.1 Decision boundary

This plan belongs to MEAS1. It does not amend AQ4.

- AQ4 Option A is already owner-approved: `C ≥ 2P`, equality passes.
- This plan does not adopt the AQ4 proposal's Q2–Q5 as separate decisions.
- This plan defines a measurement procedure for MEAS1; it does not change the approved AQ4 formula.
- Success records T6 **PASS** evidence for a later decision record. It does not close T6 by itself.
- Failure records T6 **BLOCKED** evidence. It does not authorize a payload-cap or duration-cap reduction.

### 1.2 Claim boundary

This plan can establish **packaged Wails binding transport capacity**: that the actual generated binding, JSON serialization, IPC/framing, and Go unmarshalling path of the measured packaged build can deliver the threshold field intact to the handler.

It does **not** establish:

- that the ordinary production UI accepts a 2P request; the harness intentionally bypasses only the frontend's pre-invoke `MaxBase64Chars` gate because the production UI must reject values above `P`;
- that the WAV validator accepts the threshold filler;
- that the full transcription pipeline processes the threshold filler;
- that `51,200,120` is the exact maximum capacity;
- that packaged-runtime readiness exists.

P0 is a **valid-WAV transport control**, not a WAV-validation test and not a transcription test.

## 4. Build, binding, and instrumentation identity

No measurement is valid without a complete build identity record.

### 4.1 Candidate build

The candidate must be a packaged Wails application, not `wails dev`, a browser-only harness, a mocked binding, or a Go-only call.

Record:

- repository commit SHA and branch;
- clean-worktree status or exact diff;
- build timestamp in UTC;
- Wails version;
- Go version;
- Node/npm version used for the frontend bundle;
- build command and build flags;
- packaged executable SHA-256;
- frontend bundle SHA-256;
- generated Wails binding artifacts SHA-256;
- `wails.json` SHA-256;
- code-signing state, if applicable.

If a packaged candidate does not exist, execution is blocked. This plan does not authorize creating one.

### 4.2 Generated-binding identity and harness provenance

The production target must be identified from the measured build's actual generated artifacts, not from a separately constructed test binding.

Record:

- generated module path;
- exported generated function name;
- exact request type/model name;
- generated binding identifier, if one exists;
- the generated JavaScript/TypeScript declaration and implementation hashes;
- the production frontend call site in `frontend/dist/js/audio-service.js` and its enclosing source hash;
- the test-only frontend entry point path and source hash;
- every test-harness asset loaded by the packaged WebView and its hash;
- the exact request object passed to the generated function.

The harness must invoke the same exported generated binding function used by the production frontend, with the same request model and field names. It must not:

- call `runtime.Call.ByID`;
- call `window.WailsInvoke` or an internal Wails dispatcher directly;
- use raw `postMessage`, `fetch`, `XMLHttpRequest`, WebSocket, or another transport;
- call the Go method directly;
- construct a parallel binding, proxy, or replacement request model.

The packaged WebView must load the actual generated binding artifacts from the measured build. The harness must not shadow, monkey-patch, replace, or re-register the generated binding.

A source-level comparison must show that request construction and generated-function invocation are identical to production except for bypassing the production frontend's pre-invoke `MaxBase64Chars` check. The exact allowed difference is the cap-check bypass and the measurement harness entry/exit. Any other difference invalidates the measurement.

This proves generated Wails binding transport capacity. It does **not** prove that the ordinary production UI would accept a 2P request; the production UI is required to reject it.

### 4.3 Measurement-only Go hook and neutrality

The plan permits a reviewed measurement build containing a Go hook behind a dedicated build tag at the entry to `TranscribeAudio`, after the generated binding has unmarshalled the request.

The hook must:

- read `req.WAVBase64` without modifying it;
- record the received field length;
- record a **received marker** containing the monotonic timestamp, run ID, build ID, correlation ID, and length before hashing;
- compute a SHA-256 over the received string without creating a full payload-sized copy;
- record the completed digest;
- return a structured measurement result or a controlled rejection without entering WAV validation, base64 decoding, provider access, or transcription;
- never log the payload, audio bytes, or user data.

The hash implementation must be specified in the reviewed instrumentation diff and must:

- use a streaming SHA-256 implementation;
- process the string in fixed-size chunks, proposed at 64 KiB;
- use a reusable chunk buffer where possible;
- never convert the complete payload with `[]byte(req.WAVBase64)` or an equivalent full-size copy;
- avoid retaining the payload beyond the handler call.

Before execution, the Measurement Owner must record an allocation analysis for the hook:

- allocations caused before receipt: none from the hook;
- allocations at receipt: the existing binding/unmarshalling payload, untouched;
- allocations after receipt: hash state, fixed-size chunk buffer, and log/result records;
- measured incremental heap and allocation count for the hook;
- peak additional hook allocation must remain below **1 MiB** and no single hook allocation may scale with payload length.

If the hash implementation or measured overhead exceeds those limits, the instrumentation is invalid and execution is blocked.

#### Instrumentation asymmetry

The hook cannot affect bytes that have already crossed the binding and unmarshalling boundary. It can nevertheless cause a post-receipt OOM, timeout, or logging failure that prevents evidence.

Therefore:

- a failure before the received marker is potential capacity evidence;
- a failure after the received marker but before digest completion is **INCONCLUSIVE INSTRUMENTATION**, not proof that `C < 2P`;
- an instrumentation-induced failure leaves T6 BLOCKED until the instrumentation is corrected and the plan is reviewed again;
- a successful result requires a completed digest and matching sent/received identities.

The hook must be accompanied by a reviewed source diff. A general assertion that it is measurement-only is insufficient.

### 4.4 Build-fidelity rule

The measurement build may differ from the release candidate only by the reviewed Go hook and test-only binding harness. The exact diff must be hashed and reviewed.

The generated binding signature, request model, JSON field names, IPC/framing path, and Go unmarshalling path must be unchanged. If the pre-binding path must be changed beyond the cap-check bypass, the measurement is invalid and T6 is BLOCKED pending a new reviewed plan.

The measurement build is not a release artifact and does not authorize producing a release build.

## 5. Environment and trial conditions

### 5.1 Fixed environment identity

All valid trials must run on the same environment.

Record:

- operating-system edition, version, and exact build number;
- target architecture;
- WebView2 runtime version and channel;
- Wails version and build mode;
- packaged application build ID and executable hash;
- CPU model, physical/logical core count, and total RAM;
- virtualization or container state, if any;
- power source and power plan;
- display/GPU driver information, if available;
- locale and time zone;
- user session identifier;
- application-data directory hash and WebView2 user-data profile hash;
- start time in UTC for each trial.

No OS, WebView2, driver, build, hardware, user-session, or app-data change may occur during the run. Such a change invalidates the comparison and requires a fresh run.

No network access to an ASR provider is required. The measurement stops at the handler.

### 5.2 Per-trial operating conditions

An unchanged executable and OS do not guarantee comparable memory conditions. The following are validity gates, not capacity results.

Before each launch and again immediately before invocation, record:

- available physical memory;
- commit headroom;
- page-file state;
- app/WebView process working set and private bytes where available;
- CPU utilization of non-measurement processes;
- thermal throttling state and current CPU frequency, if available.

A trial is invalid if any of the following is true:

- available physical memory is below **4 GiB**;
- commit headroom is below **4 GiB**;
- a non-measurement process uses more than **1 GiB** private working set or more than **25% CPU** during the trial;
- the power source changes or the power plan changes;
- thermal throttling begins or the CPU frequency cap changes materially during the trial;
- the application-data or WebView profile hash differs from the fixed baseline;
- the user session changes.

These thresholds must be recorded before the first trial and must not be changed after a capacity outcome is observed. If the machine cannot satisfy them, T6 is BLOCKED.

Record process memory at four points:

1. idle after launch and before request creation;
2. immediately before invoking the generated binding;
3. after the hook records the received marker and digest;
4. after application exit.

The entire environment must be dedicated to the measurement during each trial. Background updates, indexing, backups, compilers, browsers, and other memory-intensive activity must be stopped or recorded as invalidation.

### 5.3 Trial independence and process termination

Each counted trial is independent only when:

- the prior packaged application process tree has fully exited;
- the main process and all WebView child processes are confirmed gone;
- the application-data directory is reset from the hash-verified baseline;
- the WebView2 user-data profile is reset from the hash-verified baseline;
- the same user session and build are used;
- no process, cache, GPU state, or profile from the prior trial is reused.

After closing the application, the operator must:

1. record the main process ID and child process IDs;
2. wait for normal termination;
3. verify that every recorded process has exited;
4. if any remain after the cleanup window, terminate only those identified PIDs;
5. record exit codes and cleanup actions.

A trial started before the prior process tree is gone is invalid. Reusing a WebView process or user-data profile is invalid.

The trial order is fixed as P0, T, P0, T, P0, T. No trial may be replaced after observing its outcome. An invalid trial may be repeated only for a cause independent of the observed capacity result.

## 6. Deterministic request profiles

The request shape is fixed:

```text
TranscriptionRequest {
  WAVBase64:     string
  DurationMs:    600000
  CorrelationID: 00000000-0000-0000-0000-000000000001
}
```

No additional fields are permitted. The exact JSON field encoding and key order produced by the actual generated binding are recorded from a serialized sample. The field value is ASCII.

### 6.1 Profile P0 — valid-WAV transport control

Profile P0 is a canonical 600-second PCM WAV:

| Field | Value |
|---|---|
| Container | RIFF/WAVE |
| RIFF chunk size | 19,200,036 bytes |
| `fmt ` chunk size | 16 bytes |
| Audio format | 1 (PCM) |
| Channels | 1 (mono) |
| Sample rate | 16,000 Hz |
| Byte rate | 32,000 bytes/second |
| Block alignment | 2 bytes |
| Bits per sample | 16 |
| `data` chunk size | 19,200,000 bytes |
| Data content | digital silence (`0x00`) |
| Total file size | 19,200,044 bytes |
| Base64 encoding | standard RFC 4648, padded |
| Base64 field length | 25,600,060 characters |

The deterministic generator is:

```text
header = RIFF + uint32le(19,200,036) + WAVE +
         "fmt " + uint32le(16) + uint16le(1) + uint16le(1) +
         uint32le(16,000) + uint32le(32,000) + uint16le(2) + uint16le(16) +
         "data" + uint32le(19,200,000)
wav    = header + 19,200,000 zero bytes
base64 = RFC4648-padded-base64(wav)
```

Recorded fixture hashes:

```text
WAV SHA-256:        e14ff9e3be3d5257e57c029ea807754eaf22d1104999d69db4ec9e50e7c674d4
Base64 SHA-256:     4ea8caaa3d999337756485806beb14f6bacc6c249b5c069b8b77219e3da19041
Base64 length:      25,600,060
```

The fixture generator source and its SHA-256 must be recorded. No random data or environment-dependent encoding may be used.

P0 proves **valid-WAV transport**: a canonical WAV field of the approved size reached the handler intact through the same measured binding path. It does not prove:

- that the WAV validator accepts the fixture;
- that the transcription pipeline processes it;
- that the production UI accepts a threshold request;
- that the threshold capacity exists.

Both P0 and T use the same test-only generated-binding harness in the packaged WebView. P0 sends the normal approved-cap value; T sends the threshold value. The harness must not bypass JSON serialization, the Wails binding, IPC/framing, or Go unmarshalling, and it must not call the Go method directly. Using the production frontend UI is not required for this binding-capacity plan.

### 6.2 Profile T — threshold capacity vector

Profile T is a deterministic standard-Base64 string of exactly 51,200,120 characters:

```text
alphabet = ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789+/
payload  = alphabet repeated, then truncated to 51,200,120 characters
```

The length is a multiple of four. The string contains `+` and `/`; it exercises the full Base64 alphabet and any serializer escaping behavior. It has no padding because its length is a multiple of four.

Recorded fixture hashes:

```text
Threshold filler SHA-256: 5129398a2253b0487080c74ec56d81ac9f8b7fc1765f6897bd485138f45b45f8
Length:                   51,200,120
Modulo 4:                 0
```

The fixture generator source and its SHA-256 must be recorded.

Profile T is syntactically valid Base64 but is not a canonical WAV and is not intended to pass WAV validation. The measurement hook records receipt and stops before validation. A later WAV-validation failure is irrelevant to the payload-capacity question.

The threshold profile is invoked through the generated Wails binding from the packaged WebView test harness, because the production frontend cap correctly rejects values above `MaxBase64Chars`. The harness must not alter the binding signature, JSON field names, serialization path, IPC layer, or Go request model.

### 6.3 No alternate payloads

No team may substitute a different filler, a random payload, repeated `A` characters, a shorter string, or a larger string for Profile T. Any substitution is an invalid run. The fixed filler is required so independent teams measure the same serialized object.

## 7. Measurement procedure

### 7.1 Preflight

Before the first counted trial:

1. Record the r8, r8-freeze, proposal, build, and environment identities.
2. Verify the generated binding identity and harness provenance in §4.2.
3. Verify the Go hook, hash implementation, and harness match the reviewed diff.
4. Record the hook allocation analysis and confirm the 1 MiB/no-payload-sized-copy rule.
5. Verify the packaged executable, frontend bundle, generated bindings, and test harness hashes.
6. Generate P0 and T fixtures and verify their lengths and SHA-256 values.
7. Verify the app-data and WebView profile reset to the fixed baseline.
8. Record the per-trial memory thresholds and timeout.
9. Confirm no transcription provider, model, or network call is reachable or invoked.
10. Confirm the measurement hook stops before validation/decoding.
11. Record the exact generated-binding serialization samples for P0 and T.

Any preflight failure stops the run.

### 7.2 Counted trials

Run six valid trials, each in a fresh packaged application launch:

| Order | Profile | Count |
|---:|---|---:|
| 1 | P0 | 1 |
| 2 | T | 1 |
| 3 | P0 | 1 |
| 4 | T | 1 |
| 5 | P0 | 1 |
| 6 | T | 1 |

For each trial:

1. Confirm the prior process tree is gone and the app/WebView profile is reset.
2. Record the operating-condition baseline.
3. Launch the packaged application.
4. Confirm the build, environment, and generated binding identities have not changed.
5. Confirm the app/WebView profile hash matches the baseline.
6. Send the fixed request through the specified harness path.
7. Capture the sent field length and SHA-256.
8. Capture the received marker, length, and SHA-256 from the measurement hook.
9. Capture the outcome, duration, correlation ID, and run ID.
10. Capture post-hook memory and process state.
11. Close the application completely and verify process-tree termination.
12. Record whether the trial is valid and, if not, why.

No warm-up trial counts. No trial may be replaced after seeing its outcome; an invalid trial is rerun only under the invalid-run rule.

### 7.3 Timeout enforcement and cleanup

The fixed measurement timeout is **120,000 ms** from immediately before the generated-binding call until the hook returns its digest or controlled result.

If the timeout expires:

1. Record the last completed phase: pre-invoke, pre-received-marker, or post-received-marker.
2. Terminate the packaged application process tree.
3. Wait up to **10,000 ms** for normal termination.
4. Terminate only the identified remaining main/WebView child PIDs.
5. Verify that all recorded PIDs have exited.
6. Reset the app-data and WebView profile before the next trial.
7. Record cleanup actions and evidence.

Classification:

- timeout before the received marker: `T_TIMEOUT_PRE_RECEIPT` — valid capacity failure;
- timeout after the received marker but before digest completion: `T_TIMEOUT_POST_RECEIPT` — inconclusive instrumentation, not proof that `C < 2P`;
- timeout during P0: `P0_FAIL` — environment/path invalid, stop.

The timeout may not be changed after a capacity outcome is observed. Any change requires a new plan revision and a fresh run.

## 8. Intact-receipt criteria

A trial is `INTACT` only when all of the following are true:

- the generated binding accepted the complete request;
- the Go handler was entered;
- the received field length equals the sent field length exactly;
- the completed received field SHA-256 equals the sent field SHA-256;
- the correlation ID matches;
- the received marker and digest were recorded;
- no truncation, substitution, dropped character, encoding change, timeout, rejection, panic, or crash occurred before the completed digest.

A successful return value alone is not sufficient. A request that was accepted but shortened is a failure. A hook that records only a length is insufficient; the SHA-256 comparison is mandatory.

The receiver SHA-256 is an **attestation** produced by the reviewed measurement hook. Because the received payload is not retained, the independent reviewer cannot recompute it from bytes. The reviewer can verify the hook source and build, the received marker, the logs, and the equality of sender/receiver hashes. The plan must not imply that the reviewer can independently reconstruct the received payload.

The measurement records total serialized request bytes only as a diagnostic. The decision uses field-value character length. Total request bytes are never compared directly with `P` or `2P`.

## 9. Reproducibility and trial validity

T6 evidence is admissible only if:

- all three P0 trials are `INTACT` with length 25,600,060 and the recorded P0 hash;
- all three T trials are `INTACT` with length 51,200,120 and the recorded T hash;
- all six trials use the same build, environment, and operating-condition thresholds;
- the generated binding, harness, and serialization samples are unchanged across trials;
- no invalid-run correction changes the payload profile, build, environment, or instrumentation.

A result is not reproducible if the three T trials differ in length, hash, outcome, build, environment, or per-trial validity.

Invalid runs do not count toward the three required trials. Invalid-run causes include:

- wrong build, executable, binding, or harness hash;
- wrong payload hash or length;
- changed environment or operating conditions outside the thresholds;
- app/WebView profile not reset;
- prior process tree not terminated;
- harness or instrumentation mismatch;
- malformed request envelope;
- missing sent/received hash or received marker;
- logging or evidence loss;
- post-receipt instrumentation timeout/OOM.

If three valid T trials cannot be obtained, T6 is **BLOCKED**.

## 10. Failure classification

| Class | Meaning | Effect |
|---|---|---|
| `P0_INTACT` | Valid-WAV control reached the handler with matching length/hash | Counts toward P0 control |
| `T_INTACT` | Threshold request reached the handler with matching length/hash | Counts toward T6 evidence |
| `T_TRUNCATED` | Received length or hash differs from sent | Valid capacity failure; T6 BLOCKED |
| `T_REJECTED` | Binding/Wails path rejects before the handler | Valid capacity failure; T6 BLOCKED |
| `T_TIMEOUT_PRE_RECEIPT` | Timeout before the received marker | Valid capacity failure; T6 BLOCKED |
| `T_TIMEOUT_POST_RECEIPT` | Timeout after received marker but before digest completion | Inconclusive instrumentation; T6 BLOCKED, not capacity proof |
| `T_CRASH_OR_OOM_PRE_RECEIPT` | Crash/OOM before the received marker | Valid capacity failure; T6 BLOCKED |
| `T_CRASH_OR_OOM_POST_RECEIPT` | Crash/OOM after received marker but before/after digest | Inconclusive if instrumentation causality cannot be excluded; T6 BLOCKED |
| `P0_FAIL` | The P0 control fails | Environment/path invalid; stop; T6 BLOCKED |
| `INVALID_ENV` | Build, OS, WebView, hardware, power, app-data, or session drift | Invalid trial; repeat only after restoring the fixed environment |
| `INVALID_CONDITION` | Memory/load/thermal threshold crossed | Invalid trial; do not count |
| `INVALID_HARNESS` | Wrong profile, wrong binding, direct Go/Wails internal call, serialization change, or evidence gap | Invalid trial; do not count |
| `INSTRUMENTATION_DRIFT` | Hook, hash implementation, or harness differs from reviewed diff | Entire run invalid; T6 BLOCKED until reviewed again |
| `INCONCLUSIVE_INSTRUMENTATION` | Hook/harness caused or cannot exclude an OOM, timeout, or digest failure after receipt | T6 BLOCKED; not proof that `C < 2P` |

A `T_TRUNCATED`, `T_REJECTED`, `T_TIMEOUT_PRE_RECEIPT`, or `T_CRASH_OR_OOM_PRE_RECEIPT` result is evidence that the threshold was not met. It does **not** authorize a cap reduction, a new recording duration, or a rerun with a smaller profile.

An inconclusive post-receipt instrumentation failure does not authorize a pass and does not establish a capacity failure. It requires a corrected, re-reviewed measurement design.

## 11. Pass/block decision

### 11.1 PASS

Record **T6 PASS** evidence only if:

- three of three P0 trials are `INTACT`;
- three of three T trials are `INTACT`;
- all lengths and hashes match exactly;
- all operating conditions and process-independence rules pass;
- the build, binding, harness, and environment are unchanged;
- the instrumentation allocation limit is met;
- the independent reviewer signs the evidence bundle.

The result is reported as:

```text
C_verified ≥ 51,200,120 characters
T6 PASS
```

`C_verified` is a verified lower bound. The team must not claim that 51,200,120 is the exact maximum capacity or that any larger value fails.

### 11.2 BLOCKED

Record **T6 BLOCKED** if any of the following occurs:

- no named Measurement Owner;
- no approved packaged candidate build;
- no approved measurement-only build/instrumentation;
- binding/harness provenance cannot be demonstrated;
- the P0 control fails;
- any valid T trial fails or is not intact;
- fewer than three valid T trials are obtained;
- a per-trial operating-condition or independence rule fails;
- the build, environment, binding, or harness changes;
- intact receipt cannot be demonstrated by matching length and hash;
- an instrumentation-induced post-receipt failure prevents a valid result;
- the evidence bundle is incomplete or rejected by the independent reviewer.

A BLOCKED result does not establish packaged-runtime readiness, does not establish `C`, and does not authorize changes to `MaxBase64Chars`, `MaxWAVBytes`, `MaxDecodedSeconds`, or `MaxRecordingMs`.

### 11.3 No boundary probing

This plan does not test 51,200,119 or 51,200,121. Passing at exactly 2P is sufficient for the approved `C ≥ 2P` rule. If the owner later wants an exact maximum, that is a separate exploratory measurement plan and separate authorization.

After execution is separately authorized, retain one protected evidence bundle:

```text
docs/t2.9.5b-meas1-evidence-<UTC-date>-<run-id>/
```

The bundle must contain:

- `manifest.json` — run ID, UTC timestamps, plan revision/hash, r8 hash, build hash, environment hash, profiles, outcomes, validity gates, and all evidence-file hashes;
- `environment.json` — OS, WebView2, Wails, Go, hardware, power, session, app-data/profile hashes, and exact build identity;
- `conditions.ndjson` — per-trial available physical memory, commit headroom, non-measurement load, thermal/power state, process memory at the four checkpoints, and validity decision;
- `build.json` — commit, build flags, executable hash, frontend bundle hash, generated-binding hash, harness hash, instrumentation diff hash, and hash implementation details;
- `profiles.json` — P0/T generation rules, generator hashes, lengths, and SHA-256 values;
- `envelopes.json` — per-profile serialized-envelope byte length, SHA-256, field offsets, and total request bytes; no envelope bytes retained;
