## 1. How to read this briefing

This briefing uses five evidence labels:

| Label | Meaning |
|---|---|
| **Observed** | Directly inspected in the repository, or the absence of a named artifact was directly checked. |
| **Source-derived** | Stated by the frozen design or controlling register. |
| **Calculated** | Arithmetic from stated constants. |
| **Inferred** | A reasoned consequence not directly observed or tested. |
| **Unestablished** | Not demonstrated by repository source, tests, or runtime evidence. |
| **Superseded** | A prior proposal that is replaced by a later bounded rule; it is not an approved requirement. |

Two distinctions matter throughout:

1. **A proposal is not a requirement.** A recommendation remains a recommendation until the Project Owner records a decision in a later register revision.
2. **A design rule is not an implementation fact.** The design may require canonical PCM WAV, but no canonical parser or T3/T5b implementation was found. Actual parser behavior is therefore **Unestablished**.

### Plain-language terms

- **WAV:** an audio file container. It contains labelled sections called **chunks**.
- **RIFF/WAVE:** the outer WAV container and its size fields.
- **`fmt ` chunk:** the section that describes the audio format, such as sample rate and bit depth.
- **`data` chunk:** the section holding the actual audio bytes.
- **PCM:** uncompressed audio samples. The project uses mono, 16 kHz, 16-bit PCM with a two-byte block alignment.
- **Ancillary chunk:** an optional metadata section such as `LIST` or `JUNK`. The design says there are no optional chunks beyond `fmt ` and `data`.
- **Parser:** the validation code that decides whether a WAV is acceptable before transcription.
- **Temporary directory:** a private working folder created for one transcription and deleted afterward.
- **Sidecar:** a provider-generated file, such as `input.wav.json`, written beside its input file.
- **Lease:** permission to use a shared audio resource. Validation should succeed before a lease is acquired.
- **`cbSize`:** a two-byte field in the 18-byte `fmt ` form that declares extension bytes. For PCM, it must be zero.

## 3. CL1 — Imported-file copying

### The decision

When the user imports a WAV file, should the application:

- **Option A:** copy it into a private, binding-owned temporary directory, validate the copy, and give the copy to the provider; or
- **Option B:** validate the original file and give the original path directly to the provider?

### Option A — copy first, then validate the copy

**What it does.** The binding opens the source once, checks that it is a regular file and not over the byte cap, creates a private temporary directory, copies the source into `input.wav` with a hard byte limit, validates the copied WAV, acquires a lease, and transcribes the copy.

**Bounded copying.** The copy is limited in two ways:

1. The opened source's size is checked before copying.
2. The copy stops at `MaxImportedWAVBytes + 1`; reaching that limit is a failure.

The proposal explicitly forbids an unbounded whole-file read.

**Partial-copy cleanup.** On any open, create, read, write, close, or limit failure, the binding removes the exact temporary directory it created. A partial file is never validated or transcribed.

**Temporary-directory ownership.** The binding owns the exact directory returned by its own temp-directory creation. Cleanup is contained to that directory. The source file and source directory are not cleanup targets.

**Provider sidecars.** The current recognizer derives its JSON sidecar from the input path, for example `<input>.json`. If the provider input is the private `input.wav`, the sidecar lands inside the private directory and is removed with it. The design supports this ownership model. The provider's exact write behavior is **Source-derived**, not independently verified in CL1.

**Source mutation and torn copies.** Opening the source once removes the ordinary path-reopen race, but it does **not** create an atomic snapshot. If another program changes the source while it is being copied, the copy can be a mixture of old and new bytes. The proposal does not claim otherwise.

The safety property is narrower:

- the copy is bounded;
- the copied bytes are validated;
- only a copy that passes validation is transcribed; and
- a mutation that produces an invalid WAV is rejected before a lease or provider call.

A mutation that still produces a valid WAV can yield a valid copy that does not equal any single instant of the source. Detecting that would require a lock or atomic snapshot, neither of which is established.

**User-visible consequences.**

- The source file is not modified by the binding.
- The source can be read-only, provided the operating system permits reading it.
- Importing costs one extra disk copy and temporary storage up to the file size.
- Provider sidecars do not appear beside the user's source file.
- A copy failure is reported as an import/setup failure before transcription.
- The application may take longer to begin transcription because of the copy and post-copy validation.

**Tests affected.** T4 must prove temp-directory and sidecar absence after success, error, cancellation, and panic-safe cleanup. T5b must prove the canonical file is accepted and noncanonical/oversized files are rejected before a provider call. L4 must prove a copy/setup failure makes no pipeline call. T5 must prove the legacy local-path guard remains intact. T3 remains the parser test; CL1 does not decide chunk order or `fmt ` length.

### Option B — validate and use the source path directly

**What it does.** The binding validates the original imported file and passes that path to the provider. A private temp directory is still used for recorded/base64 requests, but not for the imported source.

**Consequences.**

- No extra copy is needed.
- The provider may write its sidecar beside the user's source file because the sidecar path follows the input path. That sidecar is outside the binding-owned directory.
- The existing cleanup helper removes files only inside the recognizer's own lifetime directory. It cannot clean a sidecar beside the source.
- The source can be replaced, truncated, or removed after validation and before or during transcription. This is a validation-to-use gap.
- A read-only source or read-only source directory may fail at provider time after successful validation.
- The user's directory becomes part of the provider's working area.

### Recommendation and strongest argument against it

**Recommend CL1 Option A.** The design assigns per-transcription directory ownership and sidecar cleanup to the binding. Passing the source directly conflicts with that ownership model: the provider's JSON sidecar follows the input path, and the existing cleanup function cannot remove a file beside the user's source.

**Strongest technical argument against A:** the copy adds I/O, temporary storage, and latency, and it still does not freeze the source against concurrent mutation. If the owner is willing to accept an external sidecar beside the user's file and separately define source-mutation and read-only behavior, Option B is simpler. That is a policy choice, not a free improvement.

## 4. CL2 — WAV chunk ordering

### The decision

Must a canonical imported WAV have its single `fmt ` chunk before its single `data` chunk?

### Option A — require `fmt ` before `data`

**What it does.** The parser expects the first chunk to be `fmt `, then the next chunk to be `data`. It rejects `data` first, intervening chunks, duplicates, missing chunks, a bad RIFF size, truncation, and trailing bytes.

**Parser effect.** The parser can validate the format fields as soon as it sees `fmt `, record the data offset when it sees `data`, and complete in one forward pass without deferred format state.

**Compatibility effect.** A producer that writes `data` first is rejected before any provider call. No in-repository producer was found that emits that order. The browser encoder named by the design is absent, so its output order is **Unestablished**. The downstream `whisper-cli` behavior on a data-first file is also **Unestablished**.

### Option B — accept either order

**What it does.** The parser accepts exactly one `fmt ` and one `data` in either order. If `data` comes first, it records the data offset and length, skips over the audio payload without reading it, finds `fmt `, validates the format, and then completes the bounds and duration checks.

**Parser effect.** This is modest additional state, not a second parser. The same RIFF, chunk-size, count, duration, and trailing-byte checks still apply.

**Compatibility effect.** More producers might be accepted. But no supported producer requiring this form was identified. If the provider does not tolerate data-first input, the parser would accept a file that later fails downstream with a less precise error.

**Test effect.** T3 must cover both orders plus missing, duplicate, intervening, truncation, and trailing-byte cases for each. T5b must exercise both orders at the guard. T4 must confirm cleanup on the extra paths. The matrix is larger, but the safety assertions are not stronger.

### Recommendation and strongest argument against it

**Recommend CL2 Option A.** The WAVE format rule places the format chunk before the data chunk; the project explicitly requires a canonical WAV rather than a general lenient reader; and the provider's tolerance for data-first input is unverified.

**Strongest technical argument against A:** some real-world readers tolerate data-first files, and Option B is technically feasible at modest cost. If the owner's goal is maximum import compatibility, Option B is defensible, but it should require an explicit provider-acceptance test before the project claims end-to-end support.

**This is not an approved order rule.** CL2 remains open.

## 5. CL3 — Extended `fmt ` chunks

### The decision

The `fmt ` chunk describes the audio format. The base PCM form is 16 bytes. The 18-byte form adds a two-byte `cbSize` field. Longer forms can carry extensions. What should the project accept?

### Proposed CL3 Option A contract

| Element | Proposed rule |
|---|---|
| RIFF/WAVE header | Require `RIFF` at byte 0 and `WAVE` at byte 8. |
| RIFF size | Require the declared RIFF end to equal the file length exactly. |
| Chunk walk | Start at byte 12; require complete eight-byte headers; use checked offsets. |
| Payload bounds | A chunk's declared payload must fit inside the RIFF boundary. |
| Padding | A chunk with an odd size has exactly one required pad byte immediately after its payload. An even-sized chunk has no pad. The pad value is not constrained. |
| Trailing data | Bytes outside the declared RIFF boundary are rejected. Leftover bytes inside the boundary after the last chunk are rejected. A byte after an even-sized `data` chunk is trailing data, not a pad. |
| Chunk IDs | Accept only `fmt ` and `data`. Reject `LIST`, `JUNK`, `fact`, `bext`, `cue `, `smpl`, `id3 `, `iXML`, every unknown ID, and duplicate `fmt `/`data`. |
| `fmt ` length | Exactly 16 or exactly 18 bytes. |
| 16-byte form | Parse the base PCM fields; there is no `cbSize` field. |
| 18-byte form | Parse the same base fields and require the two-byte little-endian `cbSize` at offset 16 to be zero. |
| Longer form | Reject as an unsupported PCM extension, regardless of whether `cbSize` appears to match the remaining bytes. |
| Shorter form | Reject as an undersized `fmt ` chunk. |
| Odd `fmt ` size | Reject; a pad byte does not make 17 bytes acceptable. |
| Format tag | Require tag 1 (`PCM`). Reject compressed tags and `0xFFFE` (`WAVE_FORMAT_EXTENSIBLE`). |
| Required fields | Mono, 16 kHz, 16-bit, block align 2. |
| Data length | Must be even and must fit inside the RIFF boundary. |
| Duration | Derived from data length at 32,000 bytes per second and checked against the duration cap. |
| No byte after data | An accepted even-sized `data` chunk ends at the RIFF boundary. |

**Why ancillary chunks are excluded.** The design says imported files have “no optional chunks beyond `fmt ` and `data`” (`docs/asr-repair-design.md:216`). The policy is **Source-derived**. The parser implementation is absent, so actual enforcement is **Unestablished**. CL3-A applies the design rule rather than inventing a broader one.

If the owner wanted to allow `LIST`, `JUNK`, or other ancillary chunks, that would require a separate design change with explicit positions, bounds, padding, duplicate rules, and unknown-ID policy. CL3-A does not select that.

### Why odd sizes are handled this way

The parser still understands RIFF padding: an odd-sized chunk has one pad byte and the walk advances by `8 + size + (size & 1)`. But the accepted `fmt ` and `data` chunks are even-sized:

- odd `fmt ` sizes are rejected because only 16 and 18 are accepted;
- odd `data` sizes are rejected because PCM block alignment is two bytes and the design requires an even data length;
- odd ancillary chunks are rejected by ID before acceptance.

This resolves the earlier wording conflict. “Odd” is not a blanket rejection rule; it determines whether a pad byte is required, while the chunk's class rule determines whether that chunk is acceptable.

### Option comparison

| Option | `fmt ` rule | Main advantage | Main cost |
|---|---|---|---|
| **A (recommended)** | 16 or 18 with `cbSize == 0` | Common 16-byte and common 18-byte PCM headers work; every accepted header byte is accounted for. | Rejects longer PCM forms and `0xFFFE`, even when those might be readable. |
| **B (strict)** | Exactly 16 | Smallest header surface; exact 44-byte canonical header. | Rejects common 18-byte PCM headers. |
| **C (broad, not recommended)** | Longer than 18 when `cbSize` matches; ignore extension bytes | Broader compatibility with extended headers. | Treats undefined extension bytes as harmless without evidence; trust in a self-declared length; larger accepted surface. |

### The 18-byte header and the byte cap

**Calculated.**

- A 16-byte `fmt ` produces a 44-byte header. At 32,000 bytes per second, 600 seconds is 19,200,000 data bytes. Total: 19,200,044 bytes, exactly the cap.
- An 18-byte `fmt ` produces a 46-byte header. A 600-second file is 19,200,046 bytes, **2 bytes over** `MaxImportedWAVBytes = 19,200,044`.
- The largest 18-byte-header file under the cap has 19,199,998 data bytes, or 599.9999375 seconds.

So an 18-byte-header file can be structurally valid under CL3-A but still be rejected by the byte cap at exactly 600 seconds. This is a cap consequence, not a duration-cap change. It does not change AQ4, `P`, `2P`, or MEAS1.

### CL2 interaction

CL2 controls order; CL3 controls `fmt ` length and chunk grammar. Under CL2-A, the accepted sequence is exactly `fmt ` then `data`. Under CL2-B, either order is accepted. Under either choice, ancillary chunks are rejected and there is exactly one `fmt ` and one `data`.

### The unresolved `nAvgBytesPerSec` question

`nAvgBytesPerSec` is a field in the format header describing the average byte rate. The current CL3-A proposal does **not** check it. The design does not state it as a fixed field. This is an explicit owner choice, not a hidden requirement.

**Choice 1 — leave it unchecked (current proposal).**

- The parser validates the other fixed PCM fields and the data length but does not compare `nAvgBytesPerSec`.
- No new rejection case or test is required.
- A header with an inconsistent average-byte-rate field could still be accepted if everything else is valid.
- This preserves the current proposed contract without adding a requirement.

**Choice 2 — require validation.**

The exact rule would be:

> `nAvgBytesPerSec == nSamplesPerSec × nBlockAlign`

With the fixed fields, that is:

> `nAvgBytesPerSec == 16,000 × 2 == 32,000`

The parser would reject a mismatch, including zero or a stale value. The rule would apply to both the 16-byte and 18-byte forms. Test implications:

- T3 accepts a header with `nAvgBytesPerSec == 32,000`.
- T3 rejects values such as 0, 16,000, 31,999, 32,001, or 64,000 with a specific malformed-format error.
- T5b rejects the same mismatch before any provider call.
- The 16-byte and 18-byte forms should each have accept/reject coverage.

Compatibility implication: a valid canonical file normally has 32,000, so this is low-impact for well-formed files. It can reject malformed or nonstandard headers that the current proposal would accept. It is a new parser requirement and must be approved explicitly; it should not be added silently.

**Technical recommendation:** keep `nAvgBytesPerSec` unchecked for this decision and record it as a separate unresolved hardening question. The current contract is already a deliberate narrowing; adding another rejection rule without an owner decision would expand the change surface and the test matrix. If the owner wants strict header consistency, Choice 2 is the clean rule.

### Optional sub-16-byte test-documentation row

The proposed contract already rejects every `fmt ` shorter than 16 bytes. The T3 matrix does not currently contain an explicit sub-16-byte row. This is a **test-documentation completeness issue**, not a parser-contract gap.

A future CL3 revision could add:

| Case | T3 expected | T5b expected |
|---|---|---|
| 15-byte `fmt ` with required pad | Reject undersized `fmt `; the pad does not cure it | Reject before provider |

This would not change the accepted parser contract and should not be described as a new parser requirement.

### Recommendation and strongest argument against it

**Recommend CL3 Option A.** It accepts the two common PCM header shapes whose bytes are fully understood, rejects opaque extensions and `0xFFFE`, and applies the design's no-ancillary-chunk rule consistently.

**Strongest technical argument against A:** rejecting `WAVE_FORMAT_EXTENSIBLE` (`0xFFFE`) and all longer `fmt ` forms can reject files that some decoders would read, including some professionally produced PCM files. If broad compatibility matters more than a tightly bounded canonical contract, Option B or a separately designed extensible-PCM policy would be preferable. Option C is not recommended because “ignore the extra bytes” is not a safety argument.

**This is not an approved contract.** CL3 remains open.

## 6. IR1–IR6

IR items are recommendations, not requirements. The owner may approve, reject, or leave each unimplemented. The T2.9.5B gate requires an explicit disposition for each.

### IR1 — Copy an imported WAV into the binding-owned temp directory

**What it proposes.** Implement the copy behavior described by CL1-A: bounded copy, post-copy validation, binding-owned cleanup, and provider sidecar containment.

**Current recommendation.** Approve **only with CL1 Option A**. IR1 is not a standalone requirement.

**Technical reasoning.** The design assigns per-transcription temp ownership and sidecar cleanup to the binding. Direct source use leaves the provider writing beside the user's file and leaves cleanup outside the binding-owned directory.

**Dependencies.** CL1. If CL1-B is selected, IR1 is inapplicable and should be rejected or deferred. If CL1 is deferred, IR1 remains pending.

**If accepted.** The imported path gets a bounded copy, post-copy validation, and contained cleanup. It does not guarantee an atomic source snapshot.

**If rejected or deferred.** No copy is implemented; the source path reaches the provider directly, and the owner must separately define external-sidecar cleanup, source mutation, and read-only behavior.

**Unresolved evidence.** The provider's exact sidecar write behavior is source-derived but not independently verified. No runtime trial was performed.

**Recommendation.** Approve only if CL1-A is approved. Otherwise reject or defer.

### IR2 — Join cleanup failure with the primary error

**What it proposes.** When cleanup fails after a primary transcription or setup error, join the cleanup failure with the primary error.

**Current recommendation.** **Defer — unresolved.** Do not claim that joining preserves a frontend error classification.

**Technical reasoning.** Go's `errors.Join` can preserve multiple Go-level error members. But:

- `types.AudioError` has a `Cause` field and no `Unwrap()` method, so a cause stored only there is not traversable by `errors.Is`/`errors.As`.
- `IsRecoverable` uses a direct type assertion, not `errors.As`.
- `TranscribeAudio` logs a fixed code and returns the original error; the log code is not selected from the audio error.
- The generated Wails binding returns a Promise, and the frontend catch converts the rejection to text. No typed frontend classification is observed.
- The Wails runtime's error serialization is not in the repository.

**Dependencies.** A separately defined frontend error-classification contract, or an explicitly Go-only aggregation rule. IR2 does not depend on CL1/CL2/CL3 for its existence, but CL1 approval increases the number of cleanup paths it would cover.

**If accepted.** The owner must state whether this is only Go-level preservation or also a frontend-classification claim. The latter is not established.

**If rejected or deferred.** Cleanup failure remains unreported, separately logged, or hidden by the primary error. The project should not claim a frontend classification.

**Recommendation.** Defer. If the owner wants Go-only aggregation, define that narrower rule separately and do not describe it as preserving a frontend classification.

### IR3 — Accept `fmt ` and `data` in either order

**What it proposes.** Permit the two required chunks in either order, recording data state if `data` arrives first.

**Current recommendation.** **Reject under CL2 Option A; eligible only under CL2 Option B.**

**Technical reasoning.** Under CL2-A, a data-first file is intentionally rejected. IR3 would contradict that decision. Under CL2-B, the parser needs modest extra state and a larger test matrix.

**Dependencies.** CL2. IR3 is inapplicable under CL2-A.

**If accepted.** More files may be accepted, but the project assumes the provider tolerates data-first input. That tolerance is **Unestablished**; an explicit provider-acceptance test would be required before claiming end-to-end support.

**If rejected or deferred.** The parser remains `fmt `-first; data-first imports are rejected.

**Recommendation.** Reject under CL2-A. If the owner selects CL2-B, treat IR3 as eligible but require the provider-acceptance evidence.

### IR4 — Original proposal to accept longer `fmt ` and ignore extra bytes

**What it proposes as written.** Accept `fmt ` longer than 16 bytes and ignore the extra bytes.

**Current recommendation.** **Reject as written; replace with CL3 Option A's bounded 16/18-byte rule.**

**Technical reasoning.** Ignoring an undefined tail treats bytes of unknown meaning as harmless. It accepts vendor-specific or malformed extensions without evidence. CL3-A instead accepts only the 16-byte base form and the 18-byte form with `cbSize == 0`.

**Dependencies.** CL3. If CL3-A is approved, use the 16/18 rule. If CL3-B is approved, accept 16 only. If CL3-C is approved, reconsider; CL3-C is not recommended. If CL3 is deferred, IR4 remains unresolved.

**If accepted as written.** The parser would ignore extra bytes. **This is not recommended.**

**If rejected or replaced.** The project gets a bounded rule and a specific rejection for longer forms.

**Unresolved evidence.** Whether any supported producer needs an extensible PCM header is unestablished.

**Recommendation.** Reject the original IR4. Adopt CL3-A if the owner wants 18-byte PCM support.

### IR5 — Define specific public error-category names

**What it proposes.** Add new public error-category names for parser/import failures.

**Current recommendation.** **Reject new public names; reuse existing typed mechanisms only where the mapping is established.**

**Technical reasoning.** The repository already has `types.AudioErrorCode` and `types.AudioError`. `types.ErrCodeFormatNotSupported` is the strongest established mapping for malformed/unsupported WAV shape. The mapping for copy I/O, byte-cap, and duration-cap failures is not established. No frontend audio code is observed.

**Dependencies.** No CL dependency, but the mapping depends on the parser and copy/validation design. A new public taxonomy would require a separate design/decision.

**If accepted.** The project gains named categories but also a larger public surface, more tests, and a risk of claiming a frontend classification that does not exist.

**If rejected or deferred.** Existing codes/messages remain; some failures may use generic errors. That is acceptable until a real mapping is established.

**Recommendation.** Reject the new-name scope. Reuse `*types.AudioError` with existing codes only where the mapping is clear; leave the rest unresolved.

### IR6 — Select a JavaScript unit-test harness

**What it proposes.** Choose an exact JavaScript unit-test harness for T1/T2 JavaScript-side coverage.

**Current recommendation.** **Defer the JavaScript unit-test harness decision; do not waive MEAS1.**

**Technical reasoning.** The repository has a Playwright E2E package under `tests/e2e`, but no root `package.json` and no frontend unit-test harness. The design says not to invent a JavaScript runner or root package. MEAS1 separately requires a packaged Wails application, a test-only frontend entry point, loaded assets and hashes, provenance, and a source-level comparison. Deferring IR6 does not satisfy or waive those MEAS1 requirements.

**Dependencies.** A separate JavaScript harness decision and, separately, MEAS1's packaged harness path/provenance/hashes.

**If accepted.** The owner must select a named harness, which expands T2.9.5B scope.

**If rejected or deferred.** No new JS unit harness is created; T1/T2 JS-side unit coverage remains unclaimed. MEAS1 remains blocked on its own packaged harness.

**Recommendation.** Defer IR6 for the JS unit harness. Keep MEAS1's harness requirement separate and mandatory for measurement.

## 8. Consolidated recommendation

**These are technical recommendations, not mandatory requirements.** The mandatory items are only those explicitly fixed by the design and register, such as the imported WAV caps and canonical PCM constraints.

| Item | Recommended choice | Why | Main downside | If the owner chooses differently |
|---|---|---|---|---|
| **CL1** | **Option A — bounded copy, then validate the copy** | Keeps provider sidecars and cleanup inside binding-owned temp storage; removes the validation-to-use path switch. | Extra copy time/storage; a torn copy is still possible, though invalid results are rejected. | Option B is simpler but exposes source sidecars, source mutation, read-only behavior, and cleanup outside the binding. |
| **CL2** | **Option A — require `fmt ` before `data`** | Canonical WAVE order; deterministic parser; avoids relying on unverified provider tolerance. | Rejects data-first files that some readers might accept. | Option B is feasible but expands accepted surface and requires provider-acceptance evidence. |
| **CL3** | **Option A — 16 or 18 bytes; `cbSize == 0`; reject longer and `0xFFFE`; only `fmt `/`data`** | Fully accounts for accepted header bytes; preserves common PCM forms; applies the design's no-ancillary rule. | Rejects extensible/longer PCM headers; 18-byte 600-second file is 2 bytes over the byte cap. | Option B is stricter but rejects common 18-byte headers. | **IR5** | **Reject new public names; reuse existing typed mechanisms only where established** | Avoids a new taxonomy and a frontend-code claim that the source does not support. | Some failures may use generic errors. | A new taxonomy needs a separate design/decision and tests. |

### What can safely be deferred

- **IR2** can be deferred; CL1 can still be decided. The cleanup-error joining policy remains unresolved.
- **IR5** can be deferred; existing error codes/messages remain.
- **IR6** can be deferred for the JS unit harness; MEAS1's packaged harness remains separately blocking.
- **CL1, CL2, and CL3 cannot be treated as safely deferred for implementation readiness.** They are explicit gate items. Deferring one leaves its parser/import behavior undecided and keeps implementation unauthorized.
- **IR1, IR3, and IR4 cannot be finalized before their CL dependencies.**
