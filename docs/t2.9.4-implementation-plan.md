## 0. Accepted contracts (do not renegotiate)

1. **R1 private `initOutcome`.** Per-capability initialization outcomes stay
   private to the pipeline. Individual capability errors are preserved without
   expanding the public API.
2. **Unique TTS IDs.** Every successful TTS load is tracked under its own
   loader id until shutdown. Replacement voices must not reuse one fixed id.
   (Current `ensureTTSVoice` loads every replacement under
   `string(types.TTSPiper)` — that is the defect this contract fixes.)
3. **P6 ownership handoff.** Three distinct cleanup domains:
   - failed-provider cleanup: the loader cleans up a provider whose own
     initialization fails;
   - ASR composition cleanup: `initASR` unloads exactly the recognizers it
     loaded if chain composition fails;
   - manager-owned candidate disposal: the manager owns cleanup of
     successfully initialized providers when a candidate is rejected or
     panics.
   Critical consequence: **a successful TTS provider must survive an ASR
   failure when the manager activates the candidate in degraded mode.**
   `Pipeline.Initialize` must NOT release all providers on a partial
   failure — that would break R3 (degraded startup).
4. **Test-only manager factory.** Manager integration tests exercise the real
   pipeline and manager through the test factory only. No production App
   wiring until T2.9.6.

## 1. Corrections incorporated from independent review (mandatory)

### C1. Serialize `Shutdown` with `Initialize` on the same lifecycle lock

Observed current defect (`internal/audio/pipeline.go`): `Initialize` holds
`p.mu` for its whole body, while `Shutdown` (~line 186) unloads providers
through the loader with **no lock held**, locking `p.mu` only at the end to
nil the fields. Shutdown can therefore unload providers while `Initialize`
is still composing them.

Requirement:

- `Initialize` and `Shutdown` must acquire the **same** lifecycle lock.
- Provider I/O must happen **outside** `p.mu`: snapshot the config/plan
  under the lock, perform loads and unloads without holding it, then
  re-acquire to install results and update readiness. (This also fixes the
  current secondary defect of `Initialize` holding `p.mu` across provider
  I/O, and `ensureTTSVoice` doing the same.)

### C2. Serialize lazy TTS replacement with a dedicated replacement mutex

Observed current defect (`ensureTTSVoice`, ~line 274): the
snapshot–check–load–install sequence runs under `p.mu` with I/O inside, so
two concurrent requests for the same replacement voice can both pass the
`loadedVoice` check and load it twice — wasted loads and unpredictable
active-provider selection.

Requirement:

- Guard the replacement operation with a **separate replacement mutex**,
  not `p.mu`.
- Pattern: snapshot `ttsSynth`/`loadedVoice` under `p.mu` (or the
  replacement mutex alone if it also guards those fields — choose one
  owner and document it), release, perform the load I/O, then install
  under the lock with a re-check.
- Never hold `p.mu` during I/O.
- Each replacement load uses a **unique loader id** (contract §0.2); the
  superseded synthesizer stays tracked until shutdown.

### C3. Explicit ASR ownership bookkeeping in `initASR`

Observed current defect (`initASR`, ~line 212): recognizers are loaded in a
loop, and if `chain.Initialize` fails the function returns the error while
the successfully loaded recognizers remain tracked in the loader with no
owner — leaked on the error path.

Requirement:

- `initASR` must record **exactly the loader IDs it successfully loaded**.
- On chain-composition failure it unloads **only those IDs**.
- It must NOT infer ownership from all currently loaded IDs
  (`GetLoadedModels`), because that set can include TTS providers or
  resources belonging to another operation.

## 2. Declared limitation (must appear in implementation instructions)

**R5's panic-cleanup guarantee is proven through the manager only.**
Production App wiring does not use that manager until T2.9.6. Therefore:

- T2.9.4 may prove manager-mediated panic cleanup (R5) via the test factory.
- T2.9.4 must NOT claim the current production App path has that
  protection — it does not.
- T2.9.6 must address production manager integration before the guarantee
  can be claimed for the application.

This is not a blocker: the frozen stage boundaries deliberately defer App
wiring. Test-proven behavior must never be confused with
production-integrated behavior, in code comments, test names, or reports.

## 3. Work items

### 3.1 Context-aware loader signatures

- Thread `context.Context` through `LoadASR` / `LoadTTS`
  (`internal/audio/types/interfaces.go` ~line 330, `internal/audio/runtime/loader.go`).
- Update the single signature-only test helper in
  `internal/audio/asr/fallback/chain_test.go`. No other chain changes.
- Cancellation is advisory until proven; no behavior may depend on
  cancellation that the tests do not demonstrate.

### 3.2 Failed-provider cleanup and unique TTS ownership

- Loader cleans up a provider whose own initialization fails (failed-provider
  domain, §0.3).
- `initTTS` / `ensureTTSVoice`: unique loader id per successful load;
  superseded synthesizers remain tracked until shutdown (deliberate
  retention, not a leak).
- Delete the implicit-TTS branch: `audio_input` returns text only; speech
  requires an explicit `audio_output` request. Assert zero synthesizer calls
  during transcription.

### 3.3 Pipeline initialization transaction and per-capability outcomes

- Private per-capability outcome type (R1): preserve each capability's
  error, truthful degraded readiness (`ASRReady`/`TTSReady` reflect what
  actually initialized).
- Partial failure releases only what the failing step owns (§0.3, C3);
  surviving capabilities stay usable for degraded activation (R3).
- C1 and C2 locking discipline as specified above.

### 3.4 R1–R8 / P6 tests (`pipeline_test.go`, new file)

Cover at minimum: per-capability outcomes, degraded startup truthfulness,
exactly-once release on ordinary error and on panic (manager-mediated),
no implicit TTS, context-aware loader behavior, and the P6 ownership
handoff (failed-provider vs composition vs manager disposal). F1 remains
deferred — do not implement it.

### 3.5 Manager integration tests using only the test factory

Exercise the real pipeline + manager panic-cleanup path without touching
production App behavior. Label every such test as manager-mediated so the
§2 limitation stays visible.

### 3.6 Final verification

`go test -race`, `go vet`, and package verification for the touched
packages, run by the implementer after authorization. Gofmt clean.
