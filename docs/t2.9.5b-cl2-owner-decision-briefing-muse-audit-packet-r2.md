## 1. The exact question

> Must a canonical imported WAV contain exactly one `fmt ` chunk before exactly one `data` chunk, or may those two chunks appear in either order, with all other canonical PCM WAV requirements unchanged?

CL2 remains **OPEN** in r13. Its closure requires a written parser rule and mapping to parser tests.

## 2. The two options in plain language

### Option A — Require `fmt ` before `data`

A WAV file consists of labelled sections called **chunks**. The `fmt ` chunk describes the audio format; the `data` chunk contains the audio bytes.

Option A requires the first chunk to be `fmt `, the next chunk to be `data`, and exactly one of each. A file that puts `data` first is rejected before any provider call. So are missing or duplicate chunks, intervening chunks, a bad RIFF size, truncation, and trailing bytes other than the permitted pad byte.

This is a complete ordering policy, not merely a preference for `fmt ` somewhere earlier in the file. The proposal’s exact Option A wording also requires adjacency and rejects intervening chunks.

### Option B — Accept either order

Option B accepts exactly one `fmt ` and one `data` in either order, subject to every other canonical check.

If `data` appears first, the parser must:

- record the data chunk’s offset and declared length;
- skip the data payload without reading it;
- continue the bounded walk until `fmt ` is found;
- parse the format fields; and
- complete the data bounds and duration checks after the format state is known.

Option B is technically feasible. It adds parser state and test cases, but it is not a second parser.

### Proposal-derived technical analysis

- Option A can validate format fields immediately when `fmt ` is encountered, record the data offset and length at `data`, and complete in one forward pass without deferred format state.

## 5. DeepSeek’s recommendation

**Recommend Option A: require `fmt ` before `data`.**

The recommendation rests on the following:

1. The project already requires a canonical PCM WAV rather than a general RIFF reader.
2. Option A makes the missing order rule explicit and deterministic.
3. It rejects data-first files before a provider call instead of relying on unverified downstream tolerance.
4. Option B is feasible, but adds parser state and test cases without an established safety benefit or a demonstrated producer requirement.

This is a technical recommendation only. The Project Owner decides CL2.

### Strongest counterargument to the recommendation

If a real supported producer emits data-first WAV files, Option A rejects a file that some readers might handle, and the owner would need a conversion step or a later policy change. Option B is technically feasible at modest cost. That argument is not sufficient without evidence that such a producer is actually in scope, and Option B would still require an explicit provider-acceptance test before the project could claim end-to-end support.
