## 3. What `MaxDecodedSeconds` limits

`MaxDecodedSeconds` is a **decoded-audio duration cap**, not a Base64-length cap, WAV-byte cap, or WAV-header field.

### Browser stage

The frozen design places it:

1. after `MaxEncodedBlobBytes` is checked before decode;
2. immediately after `decodeAudioData`;
3. before `OfflineAudioContext` resampling and WAV encoding.

It therefore limits the actual decoded audio buffer before resampling and encoding. Its purpose is to prevent a compressed blob that passes the encoded-byte cap from expanding into an excessively long PCM buffer and consuming resampling/encoding work. The design's placement supports that purpose; the rationale is not stated verbatim.

### Go WAV stage

The design separately requires Go to derive duration from the validated `data` chunk:

```text
durationSeconds = dataLen / 32000
```

The design says this duration must be “within cap” and within 500 ms of the advisory `durationMs`.

The design does **not** explicitly name `MaxDecodedSeconds` as the Go-side cap. This proposal makes that mapping explicit as part of AQ3. It is an additional policy decision, not a silently assumed source requirement.

### What it does not limit

`MaxDecodedSeconds` does not limit:

- the encoded WebM blob size;
- the Base64 character count;
- the WAV byte count;
- a WAV header duration field, because canonical PCM WAV has no duration field;
- the 15-minute transcription timeout;
- the provider/model-specific `ASRModelInfo.MaxDuration`.

WAV duration is derived from the `data` chunk length. The request's `durationMs` is advisory and is checked for consistency, not used as the authoritative duration.

## 4. Recorded limits and relationships

| Limit | Recorded value | Status and stage |
|---|---:|---|
| `MaxRecordingMs` | 600,000 ms proposed | Capture timer; 600 seconds |
| `MaxEncodedBlobBytes` | 64 MiB proposed | Before `decodeAudioData`; encoded WebM |
| `MaxDecodedSeconds` | **No value recorded** | After decode; actual decoded audio |
| `MaxWAVBytes` | 19,200,044 bytes | After encoding; canonical WAV payload |
| `MaxBase64Chars` | 25,600,060 characters | Before invoke; approved AQ2 value |
| `MaxImportedDurationMs` | 600,000 ms | Imported PCM WAV guard |
| `MaxImportedWAVBytes` | 19,200,044 bytes | Imported PCM WAV guard |
| Transcription timeout | 15 minutes | Operation deadline, not audio duration |
| Provider `MaxDuration` | Model-profile value | Existing provider limit; separate from T2 |

### Recording versus decoded duration

The values converge on **600 seconds**, but the limits serve different purposes:

- `MaxRecordingMs` stops capture at the recording limit.
- `MaxDecodedSeconds` guards the actual decoded buffer before resampling and encoding.
- `MaxWAVBytes` caps the encoded WAV payload.
- `MaxImportedDurationMs` guards imported files before a manager lease.
- The 15-minute timeout limits the entire transcription operation, not audio length.

They are intentionally layered and are not interchangeable. A client can bypass the capture timer; it cannot bypass the decoded-buffer check merely by producing a small encoded blob. A valid 600-second WAV can reach exactly `MaxWAVBytes`.

## 5. Mathematical derivation

### Format assumptions

- PCM format 1
- mono
- 16,000 samples per second
- 16-bit samples
- canonical 44-byte WAV header:
  - RIFF header: 12 bytes
  - `fmt ` chunk header: 8 bytes
  - PCM `fmt ` payload: 16 bytes
  - `data` chunk header: 8 bytes

```text
bytes/second = 16,000 samples/s × 1 channel × 2 bytes/sample
             = 32,000 bytes/s
```

### Maximum data and duration

```text
max data bytes = 19,200,044 - 44
               = 19,200,000 bytes

max duration  = 19,200,000 / 32,000
              = 600.0 seconds
```

Reverse check:

```text
600 s × 32,000 bytes/s = 19,200,000 data bytes
19,200,000 + 44        = 19,200,044 total bytes
```

### Base64 relationship

```text
ceil(19,200,044 / 3) × 4 = 25,600,060 characters
```

This matches approved AQ2 `MaxBase64Chars`.

### Extended-header effect

If CL3 permits a `fmt ` chunk longer than 16 bytes, let `e` be the additional header bytes:

```text
header bytes  = 44 + e
max data      = 19,200,044 - 44 - e
max duration  = (19,200,044 - 44 - e) / 32,000
              = 600 - e / 32,000 seconds
```

AQ3 does not decide CL3. It only defines the duration cap. A 600-second file with extra header bytes would still be rejected by `MaxWAVBytes`.

## 6. Boundary behavior

| Case | Expected result | Stage |
|---|---|---|
| Exactly 600.0 s decoded | Accept | Browser decoded-duration check |
| 600 s plus one 16 kHz sample | Reject | Browser decoded-duration check |
| Exactly 600 s canonical WAV | Accept at 19,200,044 bytes | WAV byte and duration validation |
| 600 s plus one sample WAV | Reject; total would be 19,200,046 bytes | `MaxWAVBytes` / decoded guard |
| 599.9999375 s WAV | Accept; 19,199,998 data bytes + 44 = 19,200,042 | WAV validation |
| 600 s with extended `fmt ` header | Reject if total exceeds 19,200,044 | `MaxWAVBytes` |
| WAV within byte cap but over 600 s | Impossible for canonical 16 kHz mono 16-bit PCM with the minimum 44-byte header; otherwise reject at the applicable cap | WAV validation |
| WAV within 600 s but over byte cap | Possible with extra header or data bytes; reject | `MaxWAVBytes` |
| Malformed/truncated RIFF or chunk table | Reject specifically | T3 |
| Unsupported format/channels/rate/depth | Reject specifically | T3/T5b |
| Odd `data` length | Reject | T3 |
| `dataOffset + dataLen` exceeds buffer | Reject | T3 |
| Bytes after final chunk beyond one pad byte | Reject | T3 |
| `durationMs` differs by more than 500 ms | Reject | T3 consistency check |
| Exactly 500 ms difference | Not decided by AQ3 | T3 clarification |
| Base64 exactly 25,600,060 | Accept | Base64 stage |
| Base64 25,600,061 | Reject | Base64 canonicality/length stage |
| Non-finite/undefined decoded duration | Reject; specific error classification remains an owner decision (Q5) | Browser validation |

**Non-normative T3 parser implementation guidance:** When walking WAV chunks, implementations should use checked or sufficiently wide integer arithmetic. This is not an AQ3 requirement and does not change any cap or validation rule in this proposal.

The browser check should use integer sample frames rather than a floating-point duration comparison:

```text
reject when buffer.length > 600 × buffer.sampleRate
```

This accepts exactly 9,600,000 frames at 16 kHz and rejects 9,600,001 frames. The Go check should use the integer data length:

```text
reject when dataLen > 600 × 32,000
reject when dataLen > 19,200,000
```

A WAV has no duration field. The `data` chunk length is authoritative. The request's `durationMs` is advisory.

## 7. Options considered

### Option A — Explicit numeric constant

**Rule:**

```text
MaxDecodedSeconds = 600
```

**Advantages:**

- Directly testable.
- Stable against changes to the provisional recording timer.
- Does not depend on a 44-byte header assumption at runtime.
- Consistent with `MaxRecordingMs = 600,000`, `MaxImportedDurationMs = 600000`, and `MaxWAVBytes = 19,200,044`.
- Avoids coupling the decoded-buffer safety cap to T6 or to the byte cap.

**Disadvantages:**

- Repeats the 600-second value.
- Requires a consistency test if any 600-second design point changes.

**Boundary behavior:** Accept exactly 600 seconds; reject anything greater.

**T2 compatibility:** Checked after decode and before encode; Go WAV duration after structural validation.

**New policy:** It records the existing 600-second duration policy as an explicit constant and explicitly maps the Go WAV duration to the same cap.

**Assumptions:** Canonical 44-byte header is the arithmetic baseline; Go uses the same cap.

### Option B — Derive from `MaxWAVBytes`

**Rule:**

```text
MaxDecodedSeconds = (MaxWAVBytes - 44) / 32,000
                  = (19,200,044 - 44) / 32,000
                  = 600
```

**Advantages:**

- Single source of truth with the approved WAV byte cap.
- No duplicated 600 constant.

**Disadvantages:**

- `MaxWAVBytes` is an encoded payload cap, not a decoded-duration policy.
- The 44-byte header assumption is exact only for canonical headers.
- CL3 may permit longer `fmt ` chunks.
- Changes to `MaxWAVBytes` would silently change the duration cap.

**Boundary behavior:** Same as Option A for canonical WAV.

**T2 compatibility:** Compatible if resolved as a fixed configuration value.

**New policy:** No.

**Unresolved assumptions:** Canonical header length and CL3 outcome.

### Option C — Derive from `MaxRecordingMs`

**Rule:**

```text
MaxDecodedSeconds = MaxRecordingMs / 1000 = 600
```

**Advantages:**

- Keeps recording and decoded limits aligned.

**Disadvantages:**

- `MaxRecordingMs` is explicitly provisional.
- T6 may require reducing it, silently changing the decoded-duration safety cap.
- It is a capture-stage policy, not a decoded-buffer policy.
- It does not address imported files.

**Boundary behavior:** 600 now; would move if the timer limit moves.

**T2 compatibility:** Compatible, but with undesirable coupling.

**New policy:** No, but unstable.

**Unresolved assumptions:** Whether T6 will reduce the recording timer.

### Option D — No independent decoded-duration cap

Rely on `MaxWAVBytes` and `MaxBase64Chars` only.

**Rejected.** Decoding occurs before WAV encoding and Base64 creation. An encoded blob can pass the 64 MiB cap and decode to a much larger PCM buffer. That would bypass the early decoded-duration guard and violate T2's decoded-cap stage.

## 8. Recommendation

**Recommend Option A: `MaxDecodedSeconds = 600`.**

The value is supported by the recorded 600-second design points, but the design does not define a canonical runtime derivation for `MaxDecodedSeconds`. An explicit constant is safer than deriving from:

- `MaxWAVBytes`, because that is an encoded-byte cap with a header-size assumption and unresolved CL3 behavior;
- `MaxRecordingMs`, because that value is provisional and may change under T6;
- `MaxImportedDurationMs`, because that applies to imported files, not decoded browser audio.

The decision should include:

- a browser sample-frame comparison;
- an explicit Go WAV `dataLen` limit;
- preservation of the T2 stage order;
- no change to AQ2 values;
- no change to the 15-minute operation timeout.

## 9. Proposed AQ3 register wording

> **AQ3 — `MaxDecodedSeconds` — PROPOSED, NOT APPROVED**
>
> Set `MaxDecodedSeconds = 600`.
>
> `MaxDecodedSeconds` is the maximum decoded audio duration. It is not a Base64-length, WAV-byte, or WAV-header limit. In the browser, after `decodeAudioData` and before resampling or WAV encoding, reject a decoded buffer whose sample-frame count exceeds `600 × buffer.sampleRate`. For canonical WAV validation in Go, after the structural and format checks, reject when the validated `data` chunk length exceeds `19,200,000` bytes; this is the same 600-second bound at 32,000 bytes per second. The browser check remains after `MaxEncodedBlobBytes` and before encoding; the WAV byte and Base64 checks remain at their existing stages.
>
> The value is consistent with the recorded 600-second limits: `MaxRecordingMs = 600,000` proposed, `MaxImportedDurationMs = 600000`, and `MaxWAVBytes = 19,200,044` described as 600 seconds plus header. With a canonical 44-byte WAV header, `(19,200,044 − 44) / (16,000 × 2) = 600`. A 600-second canonical WAV has 19,200,000 data bytes and exactly 19,200,044 total bytes. An extended `fmt ` header reduces the data duration that fits within `MaxWAVBytes`; it does not change the 600-second duration cap.
>
> WAV has no duration field. The validated `data` length is authoritative. Malformed, truncated, unsupported, or indeterminate WAV data is rejected at T3 before any provider call and is never treated as zero duration or silently truncated to the cap. The existing advisory `durationMs` consistency check remains a T3 check and is not changed by this decision.
>
> This decision does not resolve the exact 500 ms `durationMs` boundary, does not resolve CL3 extended-`fmt ` handling, does not change `MaxWAVBytes`, `MaxBase64Chars`, `MaxRecordingMs`, `MaxImportedDurationMs`, or the 15-minute timeout, does not resolve AQ4, does not authorize implementation, and does not authorize frontend D1/T1 changes.

## 10. Owner decisions required

These are explicit owner decisions. The proposal does not silently resolve them. Q1 and Q2 are embedded in the proposed wording and require the owner's explicit approval; Q3–Q5 remain outside AQ3 and require separate directions.

**Q1 — Go-side mapping.** Decide whether to apply the same 600-second cap to the Go WAV duration check, expressed as rejecting `dataLen > 19,200,000`. The design says “within cap” but does not explicitly name `MaxDecodedSeconds` at the Go stage. The proposed wording includes this mapping.

**Q2 — Exact-600 recording boundary.** Decide whether to accept exact 600-second rejection with no tolerance. Approving this proposal means accepting that a nominal 600-second recording which decodes even slightly over 600 seconds — even by one sample — will be rejected. This proposal contains no tolerance and no early-stop margin. If a tolerance or an early timer stop is desired, that is a different rule and must be decided explicitly; it is not silently included here.

**Q3 — 500 ms boundary.** Decide separately whether “within 500 ms” includes exactly 500 ms. This is a T3 validation clarification, not an AQ3 value, and AQ3 does not decide it.

**Q4 — CL3.** Decide separately whether extended `fmt ` chunks remain accepted. AQ3 does not decide CL3; a 600-second file with extra header bytes would still fail `MaxWAVBytes`.

**Q5 — Browser decoded-duration error classification.** Decide the specific error classification when the browser decoded-audio duration is non-finite or undefined. This question applies only to the browser decoded-duration result. Go-side malformed or indeterminate WAV data remains a separate T3 rejection and is not classified by Q5. The proposed sample-frame check avoids relying on a floating-point duration, but the browser failure category still requires a decision; it is not silently resolved by AQ3.
