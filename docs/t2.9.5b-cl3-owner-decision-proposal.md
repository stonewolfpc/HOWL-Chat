## 1. Purpose

CL3 asks one narrow question:

> When a canonical WAV's single `fmt ` chunk is longer than the 16-byte PCM `WAVEFORMAT` payload, must the parser reject it, or accept some extended form?

Revision 3 also states the RIFF chunk grammar that CL3 depends on, because Revision 2 contained a wording conflict: it rejected “odd sizes” while also requiring the RIFF pad rule `8 + size + (size & 1)`.

The design requires `fmt ` length **at least** 16, fixes PCM format 1, mono, 16 kHz, 16-bit, block align 2, and requires **no optional chunks beyond `fmt ` and `data`**. It does not specify the 18-byte `cbSize` field, longer extension payloads, or the exact treatment of ancillary chunks. CL3 does not decide chunk order (CL2) or the byte/duration caps.

## 3. Exact choice

### 3.1 Shared canonical RIFF/chunk grammar

All three options below share this grammar. They differ only in which `fmt ` payload sizes are accepted.

**Boundary and header.**

- Let `L = len(buf)`.
- Require `L >= 12`, `RIFF` at bytes `[0:4]`, and `WAVE` at bytes `[8:12]`.
- Read the RIFF size field `R` as an unsigned 32-bit little-endian value at `[4:8]`.
- Require `R >= 4`, because `WAVE` occupies the first four bytes of the RIFF payload.
- Define the declared RIFF end as `E = 8 + R`, using checked arithmetic. `E` is the first byte **outside** the declared RIFF boundary.
- Require `E == L`.
  - If `E < L`, bytes `[E:L)` are **trailing data outside the declared RIFF boundary** and are rejected.
  - If `E > L`, the declared RIFF boundary exceeds the buffer and the file is truncated and rejected.
  - The design's `RIFF size field equals len(buf) - 8` requirement is the same condition as `E == L`.

**Chunk walk.**

- The chunk region is `[12:E)`. The first chunk header starts at offset 12.
- A chunk header is exactly eight bytes: a four-byte ID and a four-byte little-endian size `s`.
- At each chunk offset:
  - If `offset == E`, the walk is complete.
  - If `E - offset < 8`, there is an incomplete chunk header inside the RIFF boundary; reject as trailing/incomplete chunk data. This covers one through seven leftover bytes.
  - Read the ID and `s`; let `p = offset + 8`, `payloadEnd = p + s`, and `paddedEnd = payloadEnd + (s & 1)`.
  - Require `payloadEnd <= E`; otherwise the declared payload is truncated and the file is rejected.
  - If `s` is odd, require `paddedEnd <= E`; the pad byte at `payloadEnd` must exist inside the RIFF boundary. If it does not, the pad is truncated and the file is rejected.
  - If `s` is even, `paddedEnd == payloadEnd`; there is no pad.
  - Advance to `paddedEnd`, not `payloadEnd`, for the next chunk.
- Use checked or sufficiently wide arithmetic; a 32-bit size must not wrap the computed end offsets.

**Padding rule and odd sizes.**

Oddness is **not by itself a rejection reason**. It determines whether one pad byte is required:

- A chunk with odd `s` has exactly one pad byte immediately after its payload, at `payloadEnd`. The pad is outside the declared chunk size, is not part of the payload, and must lie inside the RIFF boundary.
- A chunk with even `s` has no pad byte. A byte after an even-sized chunk is the next chunk header or trailing data; it is never a pad.
- The pad byte's value is not constrained by this packet. The design requires the pad to exist and fixes the advance; it does not require a zero value. No zero-pad rule is added here.
- Acceptance still depends on the chunk ID and that chunk class's size rule:
  - an **odd `fmt ` size** is rejected because `fmt ` must be exactly 16 or 18, even if a pad byte exists;
  - an **odd `data` size** is rejected because canonical PCM has a two-byte block align and the design requires an even data length, even if a pad byte exists;
  - an **odd ancillary size** never reaches an acceptance decision because ancillary chunks are rejected by ID.

This resolves the Revision 2 conflict: the walker understands and requires RIFF padding for odd-sized chunks, but the accepted `fmt ` and `data` chunks are even-sized, so their odd-size cases are rejected by their class rules, not by a blanket “odd is invalid” rule.

**End of the chunk region and trailing data.**

- After parsing exactly one `fmt ` and one `data`, require the next chunk offset to equal `E`. If it is less than `E`, the bytes are unparsed trailing data inside the declared RIFF boundary and are rejected.
- The design's “no bytes after the final chunk except one pad byte” is implemented as: only the **required** pad byte of an odd-sized final chunk may follow that chunk's payload. It is not a general one-byte trailing allowance.
- Because every accepted `fmt ` and `data` is even-sized, an accepted canonical file has **no byte after `data`** beyond the data payload. A single byte after an even-sized `data` chunk is trailing data, not a pad, and is rejected.
- A pad byte that belongs to an odd-sized chunk is not trailing data when it lies inside `E` and immediately follows that chunk's payload.
- Any byte at or beyond `E` is outside the RIFF boundary and is rejected as trailing data, regardless of whether it looks like a chunk header, a pad, or zero padding.

**Chunk IDs, positions, and duplicates.**

- Only `fmt ` and `data` are accepted.
- There must be exactly one `fmt ` and exactly one `data`.
- Any other chunk ID is rejected as an unsupported/unknown chunk. This includes `LIST`, `JUNK`, `fact`, `bext`, `cue `, `smpl`, `id3 `, `iXML`, and every unlisted ID. The parser does not skip ancillary chunks and does not use their declared sizes to ignore them.
- A second `fmt ` or a second `data` is rejected as a duplicate.
- CL3 does not decide order; CL2 controls it. Under the recommended CL2-A, the sequence is exactly `fmt ` then `data`. Under CL2-B, the two chunks may appear in either order. Under either outcome, there is no permitted position for an ancillary chunk before, between, or after them.

### 3.2 Ancillary chunks: only `fmt ` and `data` accepted

**Rule.** The canonical parser accepts only `fmt ` and `data`. It does not accept `LIST`, `JUNK`, or any other ancillary chunk in any position.

Because ancillary chunks are not accepted, there are no permitted ancillary positions, ancillary bounds exceptions, or ancillary padding rules to apply. An ancillary chunk is rejected after the generic eight-byte header and bounds/pad checks and before any payload interpretation; it is never skipped. Duplicate ancillary chunks are therefore not a separate acceptance case — the first one is already a rejection.

This is a design-level policy, not a new owner choice:

- `docs/asr-repair-design.md:216` says “no optional chunks beyond `fmt ` and `data`.”
- The parser implementation is absent, so actual parser behavior remains **Unestablished**, but the intended policy is established.

If the owner rejects that design rule, the alternatives would be a closed whitelist of ancillary IDs (for example only `LIST` and `JUNK`) with explicit position, bounds, padding, and duplicate rules, or a broader skip-all-ancillary rule with a closed or open ID policy. Neither alternative is selected by CL3-A, and either would require a separate design and decision packet. The current design is strict `fmt `/`data`-only.

### 3.3 Option A — Accept 16- or 18-byte PCM `fmt `, reject longer extensions (recommended)

**Rule.** The single `fmt ` chunk must have length exactly 16 or exactly 18 bytes.

- **Length 16:** parse the 16-byte `WAVEFORMAT` fields. There is no `cbSize` field. Accept only if all PCM fields match.
- **Length 18:** parse the first 16 bytes as `WAVEFORMATEX` base fields, then read the 16-bit little-endian `cbSize` at offset 16. Require `cbSize == 0`. Accept only if all PCM fields match. The final two bytes (offsets 16 and 17) are the two-byte `cbSize` field; they are not ignored.
- **Length less than 16:** reject as a truncated/undersized `fmt ` chunk.
- **Length greater than 18:** reject as an unsupported PCM extension, regardless of whether `cbSize` appears to match the remaining bytes. PCM `cbSize` must be zero, and this project does not define any PCM extension payload.
- **Odd length:** reject. The only accepted sizes are the even values 16 and 18. A pad byte after a 17-byte `fmt ` does not make it acceptable.
- **Unsupported format tag:** reject any `wFormatTag` other than 1, including `0xFFFE` (`WAVE_FORMAT_EXTENSIBLE`) and compressed tags. A 40-byte extensible header is not accepted merely because its SubFormat GUID might describe PCM; that would be a separate format decision.
- **Inconsistent `cbSize`:** reject an 18-byte chunk with non-zero `cbSize` because no extension bytes follow; reject a longer chunk with `cbSize == 0` because the trailing bytes are undeclared; reject a longer chunk with a matching non-zero `cbSize` because PCM extensions are not defined here.

**Required PCM fields.** For every accepted `fmt `:

- `wFormatTag == 1`
- `nChannels == 1`
- `nSamplesPerSec == 16000`
- `nBlockAlign == 2`
- `wBitsPerSample == 16`

`nAvgBytesPerSec` is not added as a new requirement by this packet; the design does not state it as a fixed field. If the owner wants it validated, that is a separate parser requirement, not an implication of CL3.

**Chunk and RIFF rules.** The shared grammar in §3.1 is mandatory, including the exact RIFF boundary, the eight-byte header, checked offsets, the pad rule for odd sizes, the no-ancillary-chunk rule, duplicate rejection, and the trailing-data rules. In particular:

- `data` length is even, and `dataOffset + dataLen <= E`.
- The only accepted chunks are `fmt ` and `data`; `LIST`, `JUNK`, `fact`, `bext`, and all unknown IDs are rejected.
- No byte follows an accepted even-sized `data` chunk.
- Duration is `dataLen / 32000` and must be within `MaxImportedDurationMs`.
- A chunk whose declared size exceeds the remaining RIFF bytes is truncated and rejected; a missing pad byte after an odd-sized chunk is also rejected.
- A declared RIFF size that is smaller than `len(buf) - 8` leaves trailing data outside the RIFF boundary and is rejected; a declared size larger than `len(buf) - 8` is truncated and rejected.

**Why this is safe without ignoring bytes.**

- The 16-byte form has no extension field.
- The 18-byte form contains exactly the base fields plus a `cbSize` field, and `cbSize == 0` is validated.
- A longer form is not accepted as an opaque tail. It is rejected because PCM does not define an extension here, and the project has no basis for deciding that arbitrary extension bytes are semantically inert.
- The parser never advances past bytes it has not accounted for. There is no “skip the rest of the `fmt ` chunk and hope” path.
- The parser does not skip ancillary chunks. A `LIST` or `JUNK` chunk is a rejection, not an ignored region.

**Technical consequences.**

| Consequence | Classification |
|---|---|
| Accepts the common 16-byte PCM header and the common 18-byte PCM header with `cbSize == 0`. | Source-derived from WAVEFORMATEX plus inference |
| Rejects `WAVE_FORMAT_EXTENSIBLE` (tag `0xFFFE`) even when its GUID might describe PCM. | Inferred from the fixed format-tag rule |
| Rejects vendor-specific or longer PCM extensions rather than interpreting or ignoring them. | Inferred |
| Rejects `LIST`, `JUNK`, and every other ancillary or unknown chunk. | Source-derived from the design's no-optional-chunks rule |
| Avoids a parser path that silently discards bytes whose meaning is unestablished. | Inferred |
| Uses the actual `fmt ` size for offsets and pad handling; no 44-byte-header assumption inside the parser. | Inferred |

| Odd-sized chunks require a pad byte; odd-sized `fmt `/`data` are still rejected by their class rules. | Source-derived plus inference |

**Byte-cap consequence (calculated).**

The 16-byte canonical header produces a 44-byte header and leaves 19,200,000 data bytes under `MaxImportedWAVBytes = 19,200,044`, so 600 seconds at 32,000 bytes/s fits exactly.

The 18-byte header produces a 46-byte header. A 600-second file is then 19,200,046 bytes, which is 2 bytes over `MaxImportedWAVBytes`. The largest 18-byte-header file under the cap has 19,199,998 data bytes, or 599.9999375 seconds. Therefore:

- an 18-byte `fmt ` import can be structurally accepted by CL3 yet still be rejected by the byte cap at exactly 600 seconds;
- this is a byte-cap consequence, not a duration-cap change; and
- `MaxImportedDurationMs`, `MaxImportedWAVBytes`, and AQ4's `P`/`2P` values are unchanged.

### 3.4 Option B — Require exactly 16 bytes

**Rule.** Require exactly 16 bytes for the single `fmt ` chunk; reject 18-byte and longer payloads with a specific unsupported-format error. The shared grammar in §3.1 — including the no-ancillary-chunk rule, pad handling, RIFF boundary, and trailing-data rules — still applies.

**Technical consequences.**

- Every accepted file has the exact 44-byte canonical header.
- The parser has the smallest possible header surface and no `cbSize` branch.
- Rejects the common 18-byte PCM `WAVEFORMATEX` form even when `cbSize == 0` and the base fields are valid.
- Keeps the byte-cap boundary exactly at 600 seconds for every accepted file.
- Avoids any decision about extension fields by rejecting the entire extended form.
- Does not change the ancillary policy: `LIST`, `JUNK`, and all other optional chunks remain rejected.

**Compatibility and failure consequences.** Lower compatibility for tools that emit an 18-byte PCM header. No downstream behavior change for 16-byte files. A rejected 18-byte file fails before a provider call with a specific error.

**Affected tests.** T3 accepts 16 and rejects 18/20; T5b rejects extended forms before a provider call; T4 confirms cleanup on rejection. The §3.3 T3 matrix applies except for the 18-byte acceptance row, which becomes a rejection.

**Dependencies.** IR4 is rejected or left unimplemented. AQ4's 44-byte assumption remains exact for accepted files. CL2 still controls order; ancillary chunks remain rejected.

**What remains unimplemented if rejected or deferred.** 18-byte PCM imports are not accepted; a future compatibility request requires a new decision.

### 3.5 Option C — Accept arbitrary declared `fmt ` extensions and ignore the tail (not recommended)

**Rule.** Accept `fmt ` longer than 18 when `cbSize == len(fmt) - 18`, ignore the extension bytes, and validate only the first 16 PCM fields. The shared grammar in §3.1 still applies: ancillary chunks are not accepted, RIFF padding is still required for odd sizes, and trailing data outside the RIFF boundary is still rejected. This option changes only the `fmt ` extension rule; it does not permit `LIST` or `JUNK`.

**Why this is not recommended.**

- It treats an undefined PCM extension as semantically inert without evidence.
- It accepts files whose extension may be vendor-specific, malformed, or relevant to another decoder.
- It creates a larger accepted surface and a larger test matrix without a demonstrated supported producer.
- It requires the parser to trust a self-declared `cbSize` rather than reject the undefined PCM form.
- The downstream provider's handling of such files is unestablished.

This option may be technically implementable, but this packet does not recommend it. “Ignore the tail” is not a safety argument.

## 4. Recommendation

**Recommend Option A: accept 16-byte PCM and 18-byte PCM with `cbSize == 0`; reject longer or undeclared extensions; accept only `fmt ` and `data`; reject ancillary and unknown chunks.**

The 16-byte form is the base PCM header. The 18-byte form is the standard `WAVEFORMATEX` shape when the PCM `cbSize` field is zero. Both have fully accounted-for bytes and fixed PCM fields. A longer form under format tag 1 is not defined by this project and cannot be accepted merely because the first 16 bytes look valid. The design's no-optional-chunks rule excludes `LIST`, `JUNK`, and every other ancillary chunk.

Option B is the stricter alternative if the owner prioritizes an exact 44-byte canonical form and is willing to reject common 18-byte headers. Option C is not recommended because it depends on ignoring bytes whose meaning is not established. Neither alternative changes the ancillary policy.

## 5. Proposed CL3 register wording

> **CL3 — `fmt ` chunk length and canonical chunk grammar — PROPOSED, NOT APPROVED**
>
> Require the single `fmt ` chunk to be exactly 16 or exactly 18 bytes. For 16 bytes, parse the base PCM fields. For 18 bytes, parse the same base fields and require the 16-bit little-endian `cbSize` at offset 16 to be zero. Reject lengths below 16, lengths above 18, odd `fmt ` lengths, non-zero `cbSize` in an 18-byte chunk, zero or mismatched `cbSize` in a longer chunk, and every `wFormatTag` other than 1, including `0xFFFE` and compressed tags.
>
> Require `wFormatTag == 1`, mono, 16 kHz, 16-bit, and block align 2. Require exactly one `fmt ` and one `data`; CL2 controls their order. Accept no other chunk IDs: reject `LIST`, `JUNK`, `fact`, `bext`, `cue `, `smpl`, `id3 `, `iXML`, every unlisted/unknown ID, and duplicate `fmt `/`data`.
>
> Enforce the RIFF boundary: `RIFF` at 0, `WAVE` at 8, RIFF size exactly `len(buf) - 8`, and no bytes outside the declared RIFF end. Reject trailing data outside the boundary and truncated RIFF boundaries. Walk chunks by `8 + size + (size & 1)` with checked offsets. A chunk with an odd size requires one pad byte immediately after its payload, inside the RIFF boundary; the pad value is not constrained. A chunk with an even size has no pad. Odd-sized `fmt ` and `data` are still rejected by their class rules; the pad rule does not make them acceptable. Reject a missing pad and any leftover incomplete chunk header. Require `data` length even and bounded, and require the walk to end exactly at the RIFF boundary. No byte may follow an accepted even-sized `data` chunk.
>
> Duration comes from the data length. The 18-byte header is 46 bytes total; at `MaxImportedWAVBytes = 19,200,044`, a 600-second 18-byte-header file is 2 bytes over the cap and is rejected at the byte cap. This decision does not change the duration cap, the byte cap, AQ4, CL2 order, or IR4; it does not authorize implementation, build, runtime, or measurement.

## 7. Review questions

1. Is the 18-byte `WAVEFORMATEX` form with `cbSize == 0` the only extended PCM form the project should accept?
2. Should an 18-byte header be accepted when it makes a nominal 600-second file 2 bytes over the byte cap, or should the cap force rejection?
3. Is rejecting `WAVE_FORMAT_EXTENSIBLE` (tag `0xFFFE`) even when its GUID might be PCM the intended scope?
4. Does rejecting every `fmt ` length above 18 avoid the unsafe “ignore the tail” behavior?
5. Does the owner agree that the design's “no optional chunks beyond `fmt ` and `data`” rule should be enforced as a hard rejection of `LIST`, `JUNK`, and all unknown chunks, rather than treated as merely descriptive? If not, a separate design revision is required.
6. Are odd `fmt `/`data` sizes, required pad bytes, missing pads, incomplete headers, RIFF-boundary mismatch, and trailing bytes covered by the T3 matrix with the exact expected outcomes in §3.3?
