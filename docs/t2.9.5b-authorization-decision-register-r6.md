**Verified evidence:**

### AQ2 options

| Option | Wire representation | Cap | Status | Assessment |
|---|---|---|---|---|
| **A** | Standard RFC 4648 base64 with required `=` padding | **25,600,060** | **OWNER APPROVED — 2026-11-03** | Matches normal browser `btoa` output and Go `base64.StdEncoding`; corrects the one-character arithmetic error without changing the audio byte or duration limit. |
| **B** | Raw/unpadded base64 | **25,600,059** | Alternative | Preserves the frozen constant, but requires custom padding removal and restoration in both frontend and Go. |
| **C** | Accept both padded and unpadded | **25,600,060** | Alternative | Maximizes compatibility but abandons a single canonical wire format and weakens T1/T2 validation. |
| **D** | Reduce the WAV byte limit to preserve 25,600,059 | Reduced below `19,200,044` | **Rejected** | Padded base64 lengths are multiples of four, so 25,600,059 cannot be a padded length; this would reduce audio capacity to preserve a mistaken character count. |

### AQ2 arithmetic

- `MaxWAVBytes = 19,200,044` bytes.
- `ceil(4 × 19,200,044 / 3) = 25,600,059` characters.
- Actual standard padded base64 output for 19,200,044 bytes is **25,600,060** characters.
- Option A preserves `MaxWAVBytes = 19,200,044` and the existing audio-duration limit; it corrects only the character-count cap.

### AQ2 decision and rationale

**Owner decision: Option A — standard padded base64 with `MaxBase64Chars = 25,600,060`.**

- It is the least disruptive technically sound resolution.
- It is a one-character correction.
- It changes neither the WAV byte cap nor the audio-duration limit.
- It avoids custom padding code.
- It keeps browser and Go behavior aligned.
- It maps the request round trip to T1 and the cap to T2.

Option A is the owner-approved decision; this closure is not implementation authorization.

### Approved AQ2 wording — OWNER APPROVED 2026-11-03

> **AQ2 — Base64 wire representation and cap**
>
> Use standard RFC 4648 base64 with required `=` padding for the `WAVBase64` wire field. Set `MaxBase64Chars = 25,600,060`, the padded encoding length of `MaxWAVBytes = 19,200,044`. The Go decoder must use padded standard base64, and the frontend encoder must emit padded standard base64. The length check remains before base64 decode and invoke, preserving the frozen T2 stage order in which the decoded, WAV, and base64 caps each reject at their stage (`docs/asr-repair-design.md:1097-1103`). Input that is not canonical padded standard base64 — missing or incorrect `=` padding, non-alphabet characters, or a length not a multiple of four — is rejected at the base64 stage with a specific error before decode and invoke. Unpadded input is not silently repaired or re-padded. This corrects the frozen `ceil(4/3 × MaxWAVBytes)` arithmetic from 25,600,059 to 25,600,060 without changing `MaxWAVBytes`, `MaxRecordingMs`, or any audio duration limit. Map the request round trip to T1 and the cap to T2. This decision does not resolve AQ3 (`MaxDecodedSeconds`) or AQ4 (T6 margin), does not authorize implementation, and does not authorize frontend D1/T1 changes. Canonical validation must be strict: CR and LF characters are rejected rather than skipped, and trailing pad bits must be zero (RFC 4648 §3.5), enforced either with Go `base64.StdEncoding.Strict()` plus explicit CR/LF rejection, or with a decode-and-re-encode equality check against the received string.

**Scope boundaries for this decision:**

- AQ2 does not resolve AQ3 (`MaxDecodedSeconds`).
- AQ2 does not resolve AQ4 (T6 margin).
- AQ2 does not authorize implementation, source changes, tests, frontend changes, generated bindings, builds, benchmarks, or runtime execution.
- Frontend WAV encoding, base64 handling, `audio-service.js`, `index.html`, and generated Wails bindings remain D1/T1 transport work.
- The current frontend still records WebM and calls the old string binding; this decision does not change that behavior.
- The current source has no verified `btoa`, `atob`, or WAV/base64 encoder in the reviewed frontend path.

**AQ4 dependency (not an AQ4 decision):** If this option is approved, the AQ4 margin equation takes `MaxBase64Chars = 25,600,060` as its input; the comparison formula itself remains AQ4's open question.

**Muse review history:** r3 review returned **PASS WITH CAVEATS**; F1 was incorporated as a required correction, and F2–F3 as recommended clarifications. r4 review returned **PASS WITH CAVEATS** and identified the F1 canonicality finding: strict rejection of CR and LF and zero trailing pad bits must be explicit. r5 appends that clarification to the proposed wording.
