This proposal isolates AQ4 and asks the owner to decide one thing: **what exact comparison and outcome rule makes T6 pass, require reduction, or become BLOCKED**.

AQ4 cannot claim a timer-only reduction establishes the required binding margin.

## 3. The exact AQ4 question

The frozen register asks:

> How is T6’s “2× margin” calculated?  
> Does “below `MaxBase64Chars` with a 2× margin” mean the measured ceiling must be at least twice `MaxBase64Chars`, or a different comparison? This determines whether T6 passes, requires a cap reduction, or is BLOCKED.

In plain language, AQ4 must resolve five things:

1. **Payload cap:** confirm the fixed input is the approved `MaxBase64Chars = 25,600,060`.
2. **Measured ceiling:** define what the T6 ceiling `C` measures and in what unit, including the complete request path and fixed-envelope overhead, so it can be compared to the character cap.
3. **Comparison:** decide whether T6 passes only when `C ≥ 2 × MaxBase64Chars`, or under a different two-times interpretation.
4. **Boundary:** decide whether exact equality passes.
5. **Outcome rule:** specify what happens when the comparison fails, including whether “reduce `MaxRecordingMs`” alone is sufficient, and when T6 is BLOCKED.

AQ4 is not the measurement itself. MEAS1 remains responsible for who measures, in what packaged environment, and when. AQ4 only defines the rule that consumes the measurement.

## 5. Definitions and unit rule

For this proposal:

```text
P = MaxBase64Chars
  = 25,600,060 characters
```

`P` is the approved maximum length of the `WAVBase64` string, not the total JSON request size.

```text
C = the largest WAVBase64 field-value length, in characters, that one
    complete production-shaped TranscribeAudio request can carry intact
    from the packaged frontend through the complete request path into the
    Go handler and be received there without rejection, truncation,
    character substitution, loss, timeout, or other failure
```

The definition is operational only when all of the following conditions hold:

1. **Actual packaged application.** `C` is measured on the same packaged application build and version, on the same target OS and architecture, as the build whose readiness is being assessed. A `wails dev` build, browser-only harness, mocked binding, generated-model test, direct handler invocation, or a measurement that substitutes another runtime does not produce `C`.
2. **Complete request path.** The measured value must traverse the actual path: frontend construction of `WAVBase64`, JSON serialization, the Wails generated binding, IPC and framing, any transport layer, Go unmarshalling, and entry into `TranscribeAudio`. The field must be received intact at that handler before validation, decoding, or transcription. A measurement that bypasses or substitutes any layer is not a measurement of `C`.
3. **One fixed, recorded envelope.** The request shape, `CorrelationID` length, `DurationMs` field, JSON encoding and escaping, Wails version and binding mode, IPC and framing configuration, and all other fixed-envelope settings must be recorded and held constant. A different envelope is a different measurement; a previous `C` does not carry over.
4. **Field-value unit only.** `C` counts characters in the `WAVBase64` string value. JSON quotes and the property name, braces and separators, IPC and framing bytes, and every other request byte are excluded. Base64 characters are ASCII, so one field character occupies one byte inside the field value, but total request bytes are **not** equivalent to `C`.
5. **Intact receipt.** The measurement record must demonstrate that the complete field arrived at the Go handler with the same character length and content that were sent, using a digest or equivalent preserved-value check. A success return, request acceptance, log entry, absence of an exception, or partial receipt is insufficient. A field that was truncated, altered, replaced, or dropped does not contribute to `C`.
6. **Byte-based records.** If only complete request bytes can be observed, the same request path and fixed envelope must be measured separately for overhead, and `C = total request bytes - envelope bytes`. The subtraction must be validated by the intact-receipt check in condition 5. Raw total request bytes must not be compared with `P`. If the overhead cannot be isolated or held fixed, or intact receipt cannot be demonstrated, no valid `C` exists and T6 is BLOCKED.

This operational definition is a proposed part of AQ4. It constrains what may count as `C`; it does not select the MEAS1 measurement owner, procedure, or timing. It is not stated mechanically in the frozen design.

## 6. Arithmetic

### 6.1 Base cap

```text
P = 25,600,060 characters
2P = 51,200,120 characters
3P = 76,800,180 characters
```

### 6.2 Relationship to the WAV cap

```text
WAV bytes at 600 s = 44 + (16,000 × 2 × 600)
                   = 44 + 19,200,000
                   = 19,200,044 bytes

Padded base64 = 4 × ceil(19,200,044 / 3)
              = 4 × 6,400,015
              = 25,600,060 characters
```

This reproduces the approved AQ2 cap. It is an arithmetic check, not a new cap decision.

### 6.3 Candidate pass thresholds

| Interpretation | Required measured ceiling | Payload utilization at cap |
|---|---:|---:|
| One-times minimum | 25,600,060 characters | 100% |
| **Two-times capacity margin** | **51,200,120 characters** | **50%** |
| Two-times unused headroom | 76,800,180 characters | 33.3% |

The one-times row does not satisfy the design’s express “2× margin” language. The two-times-unused-headroom row is a stricter risk policy, not the literal “at least twice `MaxBase64Chars`” comparison named in the register.

### 6.4 Boundary cases

Under the recommended two-times-capacity rule:

| Case | Result |
|---|---|
| `C = 51,200,120` | Pass; equality is sufficient |
| `C = 51,200,119` | Does not pass at the 600-second cap; short by one character |
| `C = 51,200,032` | Can pass only after a cap-consistent reduction to a 599,999 ms maximum |
| `C = 25,600,060` | Fails the two-times rule; at most a one-times fit |
| `C` unmeasured or non-reproducible | BLOCKED |
| `C` negative or otherwise invalid | BLOCKED |

The 599,999 ms example is mechanical, not a proposed recording duration:

```text
D = 599,999 ms
WAV bytes = 44 + 32 × 599,999 = 19,200,012
base64    = 4 × ceil(19,200,012 / 3)
          = 25,600,016 characters
2P(D)     = 51,200,032 characters
```

That reduced cap would fit `C = 51,200,032` exactly, but the duration and cap changes would require a separate owner decision.

### 6.5 Reduction formula

If a reduction is pursued, the mechanical target is:

```text
P_target = floor(C / 2)

B(D_ms) = 44 + 32 × D_ms
P(D_ms) = 4 × ceil(B(D_ms) / 3)

D_max = the largest integer millisecond value for which
        P(D_max) ≤ P_target
```

This formula assumes:

- canonical PCM WAV;
- mono;
- 16 kHz;
- 16-bit samples;
- a 44-byte header;
- an integer `MaxRecordingMs`.

CL3 remains open. If extended `fmt ` headers are approved, the reduction calculation must use the actual permitted header length. AQ4 does not resolve CL3.

The formula does not itself authorize changing `MaxRecordingMs`, `MaxWAVBytes`, `MaxBase64Chars`, or `MaxDecodedSeconds`.

## 7. The timer-only reduction problem

The frozen design says:

> If it is below `MaxBase64Chars` with a 2× margin, reduce `MaxRecordingMs`; never raise the ceiling without measurement.

That instruction is not sufficient by itself.

- `MaxRecordingMs` is enforced by the browser capture timer (`docs/asr-repair-design.md:257`).
- Go receives `durationMs` as advisory and derives authoritative duration from the WAV data (`docs/asr-repair-design.md:239-244`).
- AQ3 approves a Go-side 600-second bound and explicitly rejects even one sample over (`docs/t2.9.5b-authorization-decision-register-r7.md:80`, `:227-252`).
- `MaxBase64Chars` remains 25,600,060 and `MaxWAVBytes` remains 19,200,044 unless separately changed.
- Therefore, reducing only the browser timer does not reduce the maximum payload that the binding can be asked to carry, nor the maximum that Go will accept.

This is source-derived and calculated, not measured. It means:

- a timer-only reduction may improve normal-client behavior;
- a timer-only reduction does **not** establish the 2× binding margin;
- a T6 “REDUCE” outcome must either lower an enforceable request cap or return to the owner for a separate decision.

AQ4 cannot silently reopen AQ2 or AQ3. Any change to `MaxBase64Chars`, `MaxWAVBytes`, or `MaxDecodedSeconds` requires its own explicit decision and record revision.

## 8. Alternatives

### Option A — Two-times enforceable-capacity margin — RECOMMENDED

**Rule:**

```text
T6 passes when C ≥ 2P.
Equality passes.
P = 25,600,060, so the minimum passing ceiling is 51,200,120 characters.
```

**If the comparison fails:**

- T6 does not pass.
- A reduction may be considered only as a new, explicit cap package that lowers the enforceable maximum payload so that `2P_reduced ≤ C`.
- Lowering the browser timer alone is insufficient.
- If no cap-consistent reduction is approved, T6 is BLOCKED.
- A failed measurement is not converted into a pass by narrowing the browser timer.

**Advantages:**

- Matches the register’s plain-language “at least twice `MaxBase64Chars`” interpretation.
- Leaves 50% of the measured ceiling unused at the cap.
- Uses one exact integer boundary, `51,200,120`.
- Makes the equality case explicit.
- Keeps AQ2 and AQ3 values unchanged unless a separate decision is made.
- Makes clear that a timer-only reduction cannot satisfy the binding margin.

**Disadvantages:**

- Requires a large measured ceiling: 51,200,120 base64 characters.
- No evidence yet shows the packaged Wails runtime can carry that payload.
- If the ceiling is lower, the required reduction may be substantial and may need a new duration/cap package.
- The unit of `C` must be fixed before the measurement is usable.

### Option B — Two-times unused headroom

**Rule:**

```text
T6 passes when C ≥ 3P.
P = 25,600,060, so the minimum passing ceiling is 76,800,180 characters.
```

This interpretation treats “2× margin” as two full payload widths of unused space above the payload, not as a two-times capacity factor.

**Advantages:**

- Stronger operational headroom.
- More tolerant of platform overhead, serialization variance, and measurement error.

**Disadvantages:**

- Not the comparison named in the register question (“at least twice `MaxBase64Chars`”).
- Requires 50% more measured ceiling than Option A.
- Increases the chance of a large recording-duration reduction without source evidence that the extra margin is needed.
- Still requires the same enforceable-cap reduction rule; timer-only reduction remains insufficient.

Option B is a legitimate stricter policy choice, but it is not the recommended reading of the frozen wording.

### Rejected readings

- **One-times minimum (`C ≥ P`):** ignores the express 2× margin and permits 100% utilization. Rejected.
- **Literal “below by two times” (`C ≥ P/2`):** would allow the payload cap to exceed the measured ceiling and is unsafe. Rejected.
- **No precommitted formula:** leaves T6 unable to pass deterministically and does not supply the closure evidence AQ4 requires. Not recommended.

---

## 9. Recommendation

**Recommend Option A: two-times enforceable-capacity margin.**

The reasons are:

1. It is the only reading that directly matches the register’s “at least twice `MaxBase64Chars`” wording.
2. It gives a single reproducible boundary: `C ≥ 51,200,120`.
3. It leaves half the measured ceiling unused at the approved cap.
4. It avoids inventing a third payload width of unused headroom without evidence.
5. It keeps the approved AQ2 and AQ3 caps intact unless the owner separately approves a reduction.
6. It explicitly rejects the ineffective timer-only remedy.

The recommendation is conditional on the owner also approving:

- the definition and unit of `C`;
- the rule that equality passes;
- the rule that a failed comparison cannot be converted into a pass by reducing only the browser timer;
- the rule that any enforceable cap reduction is a separate owner decision;
- the BLOCKED conditions below.

### AQ2 — approved, but a reduction would touch it

## 14. Conditions requiring further review or a separate decision

AQ4 must return to review or a separate owner decision if any of the following occurs:

1. The packaged-runtime measurement cannot produce a reproducible `C`.
2. `C` is measured in bytes and the envelope overhead cannot be separated or fixed.
3. `C < 2P`, requiring a lower duration or payload cap.
4. A proposed reduction changes `MaxBase64Chars`, `MaxWAVBytes`, or `MaxDecodedSeconds`.
5. The owner prefers the stricter `C ≥ 3P` interpretation.
6. CL3 changes the permitted header size used in the reduction calculation.
7. The measurement environment or request shape changes after the T6 record is created.
8. The measurement would require raising the payload ceiling rather than reducing the recording or payload cap.
9. Any claim of packaged-runtime readiness is made before T6 passes and MEAS1 is closed.
10. Any attempt is made to treat a browser timer change as a substitute for an enforceable payload reduction.
