## 1. Purpose

CL2 asks one narrow question:

> Must a canonical imported WAV place its single `fmt ` chunk before its single `data` chunk, or may the two chunks appear in either order?

The design requires a strict chunk walk and exactly one `fmt ` and one `data` chunk, but does not state their order. This packet does not decide CL3’s `fmt ` length rule.

### 2.3 External format reference

A WAVE-format reference states that chunks may generally appear in any order except that the format chunk must precede the data chunk. This is external normative context, not repository evidence:

- WAVE file format specification, “There are no restrictions upon the order of the chunks within a WAVE file, with the exception that the Format chunk must precede the Data chunk.”  
  `http://midi.teragonaudio.com/tech/wave.htm`

The controlling project rule is still the frozen design and the owner’s eventual CL2 decision; this external reference explains why the strict rule is not merely a parser convenience.

## 3. Exact choice

### Option A — Require `fmt ` before `data` (recommended)

**Rule.** After the RIFF/WAVE header, require the first chunk to be `fmt `, require it to be the only `fmt ` chunk, then require the next chunk to be `data`, and require it to be the only `data` chunk. Reject `data` before `fmt `, any intervening chunk, duplicate `fmt `/`data`, missing either chunk, and any bytes after `data` except the single permitted pad byte, with specific malformed-WAV errors.

**Implementation shape.**

- The parser validates the first 16 PCM fields immediately when it encounters `fmt `; CL3 decides whether an 18-byte `fmt ` with `cbSize == 0` is accepted.
- The chunk walk advances by `8 + size + (size & 1)`, checks every offset against the file length, and never reads the data payload.
- The data offset and length are recorded when `data` is encountered; duration is derived from the recorded data length.
- A `data` chunk encountered before `fmt ` is rejected immediately; the parser does not defer format state.

**Technical consequences.**

- The parser can validate format fields and data bounds in one forward pass, with no deferred format state.
- The accepted form matches the WAVE ordering rule and the design’s “canonical” framing.
- Some technically readable but noncanonical WAV files with `data` first are rejected.
- The parser does not accept a file merely because a lenient reader could interpret it; it encodes the project’s canonical contract.
- The rejection is deterministic and easy to distinguish from missing/duplicate chunk errors.

**Compatibility and failure consequences.**

- A producer that emits `data` before `fmt ` will be rejected before a provider call with a specific malformed-chunk-order error.
- No in-repository producer was found that emits `data` first; the browser encoder path named by the design (`frontend/dist/js/wav-encode.js`) is absent, so its output order is unestablished.
- The downstream `whisper-cli` parser’s behavior on a `data`-first file is not established in this repository; Option A avoids depending on that unknown.

**Affected tests — exact IDs and what each establishes.**

| Test | What the test would establish |
|---|---|
| **T3** | `fmt `→`data` is accepted; `data`→`fmt ` is rejected specifically; missing `fmt `, missing `data`, duplicate `fmt `, duplicate `data`, intervening chunks, trailing bytes, RIFF-size mismatch, and truncated chunks are rejected. |
| **T5b** | A `data`-first imported WAV is rejected at the imported-file guard before any provider call; a canonical `fmt `→`data` file is accepted only within the byte/duration caps. |
| **T4** | The binding-owned temp directory is removed on the `data`-first rejection path, with no lease or provider call. |
| **L4** | Parser rejection before acquisition leaves no temp directory and makes no pipeline call. |
| **T5** | The legacy path guard remains intact; chunk-order validation does not weaken the local-path rule. |

**Dependencies.** CL3 may change how the accepted `fmt ` chunk is parsed, but not the required order. IR3 is rejected or left unimplemented under this option.

**What remains unimplemented if rejected or deferred.** No order rule exists. The parser cannot be completed deterministically for T3/T5b, and IR3 remains unresolved.

### Option B — Accept either order with deferred data recording

**Rule.** Accept exactly one `fmt ` and one `data` chunk in either order, subject to every other canonical check. When `data` is encountered first, record its offset and length and continue the bounded walk until `fmt ` is found; validate the recorded data bounds and duration after the walk, or as soon as enough state exists.

**Implementation complexity.**

- The parser needs one additional state: whether `data` was seen before `fmt `, plus the recorded data offset/length.
- It must still reject duplicate `fmt `/`data`, missing chunks, intervening non-`fmt`/`data` chunks, RIFF-size mismatch, truncation, and trailing bytes.
- If `data` is first, the walk must skip the data payload by its declared size to reach `fmt `; it must not read the payload. That is a bounded seek/skip, not an audio read, but it does mean the parser cannot validate the format fields until after the data region.
- The parser must not validate a `data` length that later proves inconsistent with the file; final bounds checks remain mandatory.
- The additional implementation is modest, not a second parser. The earlier claim that either order requires a complex second pass is not supported.

**Safety consequences.**

- There is no additional safety benefit. The same RIFF-size, chunk-size, count, data-length, duration, and trailing-byte checks are required.
- Accepting either order admits a noncanonical form into the imported path. It may increase compatibility, but it also increases the set of files the project claims to support.
- If the provider rejects `data`-first input, the parser would accept a file that later fails at the provider, producing a less precise failure than a parser rejection. That provider behavior is unestablished.

**Compatibility consequences.**

- Broader import compatibility for producers that emit `data` first.
- No evidence in the repository identifies such a supported producer; the browser encoder is absent, and ffmpeg output order is not verified here.
- The downstream provider’s tolerance is unestablished.

**Test burden.**

- T3 must add both accepted orders, plus missing/duplicate/intervening/trailing-byte/truncation cases for each order.
- T5b must exercise both orders at the imported-file guard and the cap boundaries.
- T4 must confirm cleanup on both accepted orders and on the additional rejection paths.
- The test matrix is larger than Option A by the number of order-specific cases, but the safety assertions are not stronger.

**Affected tests.** T3, T5b, T4, L4, and T5 as above, with both orders in T3/T5b.

**Dependencies.** IR3 would be eligible for approval. CL3 remains independent. If CL2-B is selected, the owner should also require a provider-acceptance test before claiming end-to-end support for `data`-first files.

**What remains unimplemented if rejected or deferred.** The parser remains `fmt `-first; a future compatibility requirement would need a new decision.

## 4. Reassessment and recommendation

**Recommend Option A: require `fmt ` before `data`.**

This is not selected merely because it produces a shorter parser. The reasons are:

1. The WAVE format rule requires `fmt ` before `data`; the project’s imported form is explicitly canonical, not a general RIFF reader.
2. The parser contract should reject a noncanonical order before a provider call, not pass the ambiguity downstream.
3. No repository evidence establishes that a supported producer emits `data` first, and the downstream provider’s tolerance is unestablished.
4. Option B is technically feasible at modest cost, but it adds accepted surface and test burden without adding a safety property. If the owner wants broader compatibility, Option B is defensible only with a provider-acceptance test and an explicit compatibility goal.

**If the only argument for Option A were fewer lines of parser code, it would be insufficient.** The recommendation rests on the canonical contract, the WAVE ordering rule, and avoiding an unverified provider dependency.

**If the owner prioritizes maximum import compatibility**, Option B should be selected explicitly, with the deferred-offset parser and the additional tests above; it must not be adopted implicitly by a permissive parser.
