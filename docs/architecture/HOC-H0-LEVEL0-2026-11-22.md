## 1. What changed

`internal/host` is a new package. It owns lifecycle and coordination, and it stores no
conversation, model, audio, image or configuration value.

| File | Owns | Must not own |
|---|---|---|
| `gate.go` | admission of new work (`Stopping`, `Ensure`), single-entry idempotent shutdown (`Once`) | what shutdown does |
| `background.go` | startup work that outlives its starter; bounded join; panic containment | the work itself |
| `streams.go` | the one active generation token and its cancellation | the turn, its text, or its history |
| `processes.go` | a child process already started, its single `Wait` owner, bounded stop | whether an engine should start (runtime policy) |
| `stages.go` | ordered shutdown stages, failure accumulation, escalation callback | error formatting or logging |
| `host.go` | the `Authority` container for the four primitives | any domain state |

**Removed from `App`:** `shuttingDown`, `shutdownMu`, `shutdownCoord`, `backgroundWG`,
`streamMu`, `streamCancel`, `streamGen`, `serverMu`, `serverMonitor`, `serverProc`. The
`shutdownCoordinator` type is deleted; its behaviour moved to `host.Gate.Once`, including
the panic-to-error conversion and the shared result for waiting callers.

**Call sites retargeted** (no wrapper left to keep the old route alive): `app-model.go` ×11,
`app-prompt.go` ×5, `app-image-model.go` ×1, `app.go` ×2 (startup), `app-lifecycle.go`,
and three test files. `App` keeps `level0()` and `ensureAcceptingWork`, which is the one named
refusal route every domain asks.

`app-lifecycle.go` is now 114 lines: constant, authority accessor, `shutdown`, `runShutdown`
composed of named stages, and the refusal route. It reads the same at a glance because each
stage names its owner's call.

## 2. Level 0 contract

- **Owns:** admission, shutdown sequencing, background joining, active-stream cancellation,
  child-process supervision, and the ordered escalation of shutdown failures.
- **Must not own:** any value a domain is responsible for. A field here that stores
  conversation, model, audio, image, memory or configuration state recreates the god-object
  H0 exists to undo.
- **Failure:** a stage failure is recorded with its stage name and the sequence continues;
  a panic is recorded at critical severity. Shutdown returns one joined error.
- **Escalation:** the application supplies the sink (`a.logError`); the host supplies the
  ordering and the attribution.
- **Diagnostics are not Level 0.** Failure coordination and failure reporting are separate
  responsibilities. Level 0 owns ordering, accumulation and the invocation of the sink;
  the reporting mechanics — the structured error log and its rotation, privacy-safe report
  building/upload/saving, and the UI event payloads — belong to an application-constructed
  domain owner, `internal/diagnostics` (§19). The owner can report a failure without
  deciding what the application does about it.

## 9. D-4 and D-5 closed (2026-11-22, appended)

Both defects came from H1's own click-through. Each is fixed at the layer that owned the
failure, not by caching values or restoring state in `App`.

### 9.1 D-4 — packaged Audio Settings never hydrated

**Cause (code path).** `frontend/dist/js/wails-bridge-iframe.js` began with `if (window.go)
return;`, deferring to any native binding found inside the modal's frame. WebView2 injects the
Wails bindings into the subframe, so the panel's shim never installed and `settings-state.js`
awaited a frame-local `App.GetSettings()` that can never settle — the host IPC handler belongs
to the top-level document. Result: the panel stayed at "Loading saved audio settings…" forever
while unrelated calls (tabs, engine list) kept working. In the harness the iframe inherited the
harness shim, which answered, so the break was packaged-only.

**Fix.** A framed document now always uses the parent-host bridge (`iframe-bridge-host.js`,
which calls the real `App` bindings in the top frame); only a standalone top-level page may
prefer a native `window.go`. `audio-settings.html` loads the file as `?v=2`.

**Verified by clicks (packaged WebView2).** `hoc-h1-d4-packaged-audio-hydrated.png` — no
loading label, ASR off, TTS off. `…-scrolled.png` — TTS Output Volume **0.4** and Push-to-Talk
**on**, i.e. the values saved by the harness. Toggled Push-to-Talk off (`…-ptt-off.png`), then
**Save & Close** → modal closed (`…-save-close.png`) and `settings.json` became
`pushToTalk=false, ttsVolume=0.4, ttsSpeed=1.75, ttsEnabled=false`.

### 9.2 D-5 — leaving Chat refused its save

**Cause (code path).** `withChatLock` keeps an in-process map and returns
`RefusedReentrant` for the second entry on one conversation. No mutator nests (every one uses a
`…Locked` helper), so that code could only ever fire on *concurrent* entry, not composition.
Two frontend writers produced it: `DataSync.cleanup()` on `beforeunload` (started by
`navigateTo`) and a raw `App.SaveChat()` in `chat-state-bridge.js`, also on `beforeunload`.
Not caused by H1's migration — the chat save path was untouched.

**Fix, one route per authority.**
1. `chat-state-bridge.js` — the duplicate `beforeunload` `SaveChat` is deleted; DataSync already
   listens there.
2. `data-sync.js` — `saveCurrentChatData()` is the single serialized save route: overlapping
   callers share the in-flight write and coalesce into one trailing save.
3. `navigation.js` — `navigateTo()` awaits that one save before unloading (`howlNavigationSaved`
   suppresses the now-redundant unload save), so the write completes instead of being aborted
   mid-flight.

**Clicked then (browser harness).** Nav Chat → Image Generator: console shows
`Chat data saved successfully via SaveChatData`; the harness RPC log for the whole session
contains **zero** `refused` results and no `Failed to save chat data` / `Final save failed`.
File → Exit → `[FinalSave] committed history with 4 entries`, process exits.
**Not clicked then:** the audio panel *inside* its iframe. The save that wrote TTS Output Volume

(ASR off)") was clicked on `audio-settings.html` served as a top-level page — the same panel
document against the same backend, but not the embedded shape. That substitution was not

iframe.
**Packaged:** nav Chat → Image Generator renders (`hoc-h1-d4b-packaged-nav.png`), so the
awaited save does not block navigation in WebView2.

## 10. Harness verification of D-4/D-5, by pointer clicks inside the embedded panel (2026-11-22, appended)

The §9 harness evidence clicked `audio-settings.html` served as a top-level page. That was not
the shipped shape: the app embeds the panel in an iframe, so the harness run had to click the
panel *inside that frame*. This section replaces that substitution with pointer clicks.

### 10.1 How the clicks were delivered

The repo's browser-preview tooling cannot address nodes inside a cross-document frame, and a
`document.elementFromPoint(...).click()` inside the frame is not a pointer event. So the harness
was served to a real Chromium window (Edge, `--remote-debugging-port=9333`, same
`HOWL_WEBVIEW_DATA_DIR` isolated root) and driven through CDP by
`build/verify/cdp-drive.mjs`: each step reads the iframe's `getBoundingClientRect()` plus the
in-frame control's rect and dispatches `Input.dispatchMouseEvent` (move, press, release) at the
resulting absolute viewport coordinates. The browser routes that event into the frame, so the
embedded control receives a genuine pointer press. Plans and outputs are kept in
`build/verify/plan-harness-*.json` and `build/verify/logs/`. No frontend, bridge or harness
source was changed for this; the packaged WebView2 path is untouched.

**12.3.1 Add Folder killed the packaged app.** `OpenImageModelsDirPicker` used

## 13. Level 0 landed as a lifecycle authority (2026-11-22)

Section 12 fixed click-blocking defects and said plainly that Level 0 was not extracted. This
section is the extraction: `internal/host` now runs the application's sequence, and the image
engine's construction and teardown moved out of `App` into the image domain.

### 13.1 What is finished in code

**`internal/host` is the lifecycle authority, not a moved god-object.**

- `internal/host/lifecycle.go` — `Lifecycle` owns the ordered `Stage` list: `Boot` runs stages in
  dependency order, stops at the first failure, records per-stage `StageReport` (name, duration,
  error, panic) and flips readiness only when every stage completed; `Shutdown` closes the gate once
  and runs the teardown stages through `Stages`, accumulating failures; `Boot` after a `Shutdown`
  reopens the gate (`Gate.Reopen`) so a restart re-runs the same composition instead of a parallel
  one. It stores stage sets, readiness, epoch and reports — no conversation, model, audio, image or
  configuration value.
- `internal/host/host.go` — `Authority` now exposes `Lifecycle` beside the primitives that already
  had one job each (`Gate` admission/once, `Background` joinable work, `Streams` the one stream
  token, `Processes` child-process lifetime, `Stages` ordered failure accumulation). All five are
  used by their real callers; none was added to fill a slot.
- `app-boot.go` — the seven boot stages, in dependency order: core services → audio owner → settings
  store → content libraries → model registry → image domain → inference capture. `NewApp` is now a
  struct literal plus `Lifecycle.Boot(...)`; it no longer performs startup ordering itself.
- `app-lifecycle.go` — shutdown is a stage list (`stop in-flight work` → `background work` →
  `final chat save` → `llama-server stop` → `image engine shutdown` → `audio manager shutdown` →
  `process job close`) run by `Lifecycle.Shutdown`, with the application's error sink supplied for
  reporting.
- `app.startup` logs the readiness Level 0 reached (`[lifecycle] webview attached: boot N ready …`).

**The image domain owns the image engine; the old wiring path is gone.**

- `internal/media/image_boot.go` — `Image.Boot` constructs the gallery, the `sdcpp` engine, the job
  manager and the job→gallery sink, registers its models directory through a supplied hook, restores
  the last model and records the sd-server commit. `Image.Reconfigure` (which replaced App's
  `reinitEngine` body), `Image.EngineConfig` and `Image.SaveSettings` live here too.
- Deleted from `App`: `initImageEngine` (the whole construction block, including the gallery and job
  manager it created), the job-completion sink in `NewApp`, and `reinitEngine`'s engine-building body.
  `SetImageModelsDir`/`SetSDServerPath` still exist as bindings but now state a change and call
  `Image.Reconfigure`; `GetImageEngineConfig` and `saveImageSettings` delegate to the domain.
- `internal/image/engine/sdcpp/version.go` — sd-server version probing and the known-old-commit list
  moved into the engine package (`BinaryVersion`, `IsKnownOldVersion`), so the domain boot and the
  diagnostics binding share one cache instead of two implementations.
- `harness_main.go` — the browser host gained `/__shutdown`, which runs the same Level 0 sequence
  Wails' `OnShutdown` runs and then exits. Without it the harness could only be killed, so an orderly
  shutdown could not be exercised in that host at all.

Functionality preserved by the move: video, vision, memory, RAG, audio, libraries, registry, model
intelligence and every binding keep their existing owners; only the image session's construction
changed hands.

## 16. Runtime & Resources moved into `internal/runtime` (2026-11-23)

### 16.1 What changed

`internal/runtime` now owns the runtime session and the settings authority. It is a new
package beside `internal/resource` (hardware arbitration) and `internal/settings` (the JSON
`Store`): `resource` decides what may run, `runtime` holds what is running and how its
configuration is stored.

- **`runtime.Engine`** — the inference `Client` interface (moved out of `app.go`), the
  `*model.Manager` built on it, load progress and stage (lock-free atomics, still stored as
  progress×1000), and the bookkeeping for the last load: `Profile` and `AutoTemplate` under
  one mutex. A nil `*Engine` is an absent runtime: reads return zero values and writes are
  dropped, which keeps a partially constructed `App` (tests, probes) working without a
  second copy of progress state.
- **`runtime.Settings`** — the unified document, the live sampler and model sections, the
  legacy `sampler-settings.json`/`model-settings.json` files and the `settings.Store`.
  `Load` restores the document and each section (unified section wins, legacy file when it
  is absent) and keeps going after one bad file, returning the first error. `Replace`
  installs a caller's whole document, **replaces** the sampler/model sections it carries
  (a removed key stays removed; a section it omits is left alone) and persists it.
  `All`/`Sampler`/`Model`/`Section` return snapshots, so a caller cannot mutate the
  authority through a map it was handed; `Set*`/`Merge*` are the only writers.
- **Deleted from `App`, not shadowed:** `httpClient`, `samplerSettings`, `modelSettings`,
  `modelSettingsMu`, `appSettings`, `settingsStore`, `loadingProgress`, `loadingStage`,
  `autoTemplate`, `currentModelProfile`, the `inferenceClient` interface, and the App-side
  `saveSamplerSettingsToFile`/`loadSamplerSettingsFromFile`/`saveModelSettingsToFile`/
  `loadModelSettingsFromFile` helpers. Every call site now goes through the owner
  (`a.engine.Client()`, `a.engine.Progress()`, `a.settings.Model()`, …).
- **Boot** constructs the engine client/model manager (`bootCoreServices`), wraps the
  engine's client for prompt capture, and builds the settings owner with the sampler
  defaults (`bootSettings`). The desired audio contract is still applied by App from the
  document's `audio` section.
- Wails binding signatures are unchanged (`GetSettings`, `SetSettings`,
  `GetSamplerSettings`, `SetSamplerSettings`, `SetModelOptions`, `GetModelOptions`,
  `UpdateRuntimeSettings`, `UpdatePromptSettings`, `GetLoadingProgress`,
  `GetLoadingStage`, `IsModelLoaded`, `ResetApplicationSettings`). `UpdateRuntimeSettings`
  replaces the model section; `SetModelOptions`/`UpdatePromptSettings` merge into it, as
  before.
- Behaviour that is deliberately identical: sampler sections replace rather than merge; a
  legacy section file replaces the defaults exactly as pre-unification boot did; model
  loads still mutate the model section in memory without persisting it; discovery prefs
  still go through `SetSettings`.

### 16.2 Tests for the moved surface

- New `internal/runtime/engine_test.go`: nil-engine reads/writes are safe; progress/stage,

## 19. Diagnostics moved to `internal/diagnostics`; Level 0 stayed small (2026-11-23)

### 19.1 The contract correction

§18 blocked the row because its destination was written as "Level 0 diagnostics, once its
reporting path owns escalation". That condition conflated two responsibilities that should
cooperate, not collapse into one owner:

| Responsibility | Owner |
|---|---|
| Shutdown ordering and failure accumulation | `host.Stages` / `host.Lifecycle` |
| Escalation policy and sink | `App` |
| Error logging and rotation | Diagnostics owner (`internal/diagnostics`) |
| User-facing error reporting | Diagnostics owner (`internal/diagnostics`) |
| Wails event emission | Diagnostics owner, through an application-supplied port |
| Application context and configuration | `App` |

The approved correction was narrow: revise this document so diagnostics are
application/domain infrastructure, establish the ownership boundary, migrate the three
responsibilities and retire the old App ownership. Level 0 was not redesigned, and the §2
contract was extended with a "Diagnostics are not Level 0" bullet rather than rewritten.

### 19.2 What the new owner holds

`internal/diagnostics` (`logger.go`, `reporter.go`, `owner.go`) owns exactly the three
responsibilities and their shared lifecycle:

- **The structured error log.** `Logger` keeps the old filename
  (`<settings dir>/logs/howl-errors-YYYYMMDD.jsonl`), the old JSON keys
  (`t,c,s,op,loc,msg,ctx`), the wrapped error text as `msg`, sanitized context, the 50 MB
  rotation and the five-file retention. `SanitizeContext` moved to `internal/errors` so the
  report payload and the log share one redaction rule.
- **Reporting.** `Reporter` keeps the same upload endpoint, the same `SaveReport`
  path/`error-reporting.json` toggle semantics and the same top-level report fields. Its error
  entries no longer carry context values: §20.5 replaced them with `context_keys` after the
  payload audit. The enabled flag is
  mutex-guarded and lives in the owner, not in `App`.
- **Event emission.** `Owner.Report` emits `app:error` with the same JSON-string payload as
  before (`code, severity, operation, location, time, context_keys`); `ReportSilent` logs
  without emitting. The transport is `diagnostics.Emitter`, a two-line interface
  (`Emit(event string, data ...interface{})`). The application supplies `appDiagnosticPort`,
  which routes through the existing guarded `App.emitEvent` (Wails events in the desktop
  host, the harness `devEventSink` in the browser host). No Wails type enters the package,
  and a port that panics is contained by `Owner.emit`.

`internal/errors` now holds only the taxonomy and recovery helpers: `Code`, `Severity`,
`TrackedError`, `New`, `SanitizeContext`, and `RecoverFromPanic`/`RecoverSilent` (the latter
now takes `interface{ Log(*TrackedError) }`). `logger.go`, `reporter.go` and `wails.go` are
deleted. `Owner` is nil-safe on every method, so an App built without it (tests, partial
construction) behaves exactly like the old nil-field checks.

### 19.3 Wiring and lifecycle

- `NewApp` constructs the owner with explicit config —
  `diagnostics.Open(diagnostics.Config{LogDir: <settings dir>/logs, AppVersion: "1.0.0",
  UploadEnabled: loadErrorReportingSetting()})` — and attaches the port. This is
  host-independent: the log and reporter need no webview, and the port drops events until a
  host can consume them. Previously the initialisation ran only in Wails' `startup` callback,
  which is why the browser harness had never had a working error system; the harness now gets
  the same owner as the packaged app, and `bindErrorEmitter` no longer requires a `ctx`.
- `App` keeps policy and configuration: the persisted upload preference
  (`loadErrorReportingSetting`/`saveErrorReportingSetting`), the bindings
  (`GetErrorLog`, `SetErrorReportingEnabled`, `IsErrorReportingEnabled`, `SendErrorReport`,
  `GetErrorReportPreview`, with identical messages), and the escalation sink.
- `App.shutdown` supplies `host.ShutdownOptions{OnFailure: a.logError(...)}` unchanged and
  closes the diagnostics owner at the end of the sequence, so the sink's `SYS-SHUTDOWN` entry
  is written before the file closes. A second close is a no-op.
- The three old fields are gone; `App` holds `diagnostics *diagnostics.Owner` only. No shim,
  forwarder or shadow logger remains.

## 21. Local-state cutover: who owns it (2026-11-23)

### 21.1 The question

The renderer still references `localStorage` 197 times across `frontend/dist/js`. Some of those
are legitimate UI preferences; many are domain records that a backend owner already writes to
disk. The rule to enforce is: **the domain authority owns its data; the renderer may hold
temporary UI state or a rebuildable cache, never a competing source of truth.** This section
records the audit and the engineering decision about who owns the cutover.

### 21.2 What the audit found

| Category | Backend owner today | Renderer today | Verdict |
|---|---|---|---|
| Settings | `internal/runtime.Settings` via `GetSettings`/`SetSettings` | `settings-state.js` writes localStorage **first**, then debounces the backend write | **Inverted authority** — a failed or delayed backend write leaves the cache ahead of the file |
| Lorebooks | `internal/lorebookstore`, files in registered roots; `ListLorebooks`, `SaveLorebook`, `DeleteLorebook`, `ImportLorebooks`, `RollbackLorebookImport` | `lorebook-repository.js`: canonical read, `cutover` flag, cache written from canonical, explicit import and rollback | **Correct — the reference implementation** |
| Worlds / scenarios | `internal/worldstore` is already "the only writer" of `world.json`/`scenario.json` | No App bindings at all; pages read and write `howl-worlds` / `howl-chat-scenarios` | Store exists but is unreachable; localStorage is the de facto authority |
| Characters | App writes `Characters/<name>/character.json`; only `CreateCharacter` and `GetCharacters`, identity is the directory name | `character-storage.js` (localStorage metadata + IndexedDB blobs) is what every page uses | **Two half-authorities**; neither has update/delete/import, so neither can win |
| Image settings | `Image.SaveSettings` / backend image store | `IG_STATE_KEY` holds generation settings and UI state together | Duplicate authority for the settings half |
| Chat session | `chat.Conversation` owns the persisted chat | `howl-chat-current-session` stores a projection that re-resolves characters/worlds/scenarios/lorebooks by scanning localStorage catalogs | Cache by intent, but it is the catalog scan that makes localStorage load-bearing |
| Chat messages | `chat.Conversation` (append log, snapshots) | read-only projection | Correct |

The one category that already complies is lorebooks, and it does so because the cutover was
given to the store: `ImportLorebooks` is described as "the explicit ownership transition from
the browser store. It is create-only, idempotent, and journaled", and the browser store is
"a derived cache and the legacy source for the explicit import".

### 21.3 Decision

**The cutover is owned by each domain store, invoked once by the application composition root,
with exactly one renderer repository module per domain acting as cache.** It is not owned by a
new global migration service and not by page scripts.

- **The domain store owns the transition.** It already owns the envelope format, identity,
  validation, destination root and rollback material, so it is the only place that can import
  legacy records without creating a second authority. Semantics are the lorebook ones: explicit,
  create-only, idempotent, journaled, reversible, and never automatic (F2-C7).
- **`App` owns composition only.** It exposes the binding and calls the store; it does not parse,
  merge or reinterpret legacy records. No boot-time silent import: the backend cannot read
  localStorage, and the renderer must hand the payload over as an explicit user-visible action.
- **The renderer owns one repository module per domain**, modelled on `lorebook-repository.js`:
  hydrate from canonical, write the cache from canonical, expose `importLegacy`, `rollback` and
  the `cutover` flag, and throw on a refused write. Pages call the repository, never
  `localStorage`, for domain data.
- **Binary media stays a cache.** Image blobs may remain in IndexedDB keyed by the canonical
  media identity; their metadata follows the owning domain.

Rejected alternatives: a generic "migration service" would still need every domain's validation,
so it adds a layer without an owner; a boot-time automatic import violates F2-C7 and cannot see
the browser store; per-page adapters preserve the 20 competing writers that caused the problem.

### 21.4 Cache contract

1. A backend answer always wins; the cache is read only when the backend is unavailable or a
   cutover has not happened yet.
2. The cache is written **after** the backend acknowledges a mutation, never before.
3. The cache is versioned and rebuildable; clearing it must lose no canonical data.
4. Every mutation hydrates again before the UI reports success.
5. A wipe clears canonical data first, caches last.
6. Only repository modules and preference UI (theme, scale, panel positions, in-flight composer
   text, board drag state) may touch localStorage; domain records may not.

### 21.5 Cutover order

1. **Settings authority inversion** — backend write first, mirror localStorage only after it
   returns; keep the localStorage fallback for a backend outage, never merge it over a backend
   answer. No record migration needed.
2. **Characters** — extract a `characterstore` with the same envelope/identity/roles discipline
   as `worldstore`, add update/delete/import/rollback, then replace `character-storage.js` with a
   `character-repository.js` cache. This is the largest gap: the current identity is a directory
   name and there is no update path.
3. **Worlds and scenarios** — expose bindings over the existing `worldstore` (list/save/delete/
   import/rollback) and add the two repository modules.
4. **Image state split** — generation settings to the backend image store; `IG_STATE_KEY` keeps
   only UI state (board, pose, selection).
5. **Chat session pointer** — `howl-chat-current-session` keeps the chat id and UI selection
   only; catalogs are hydrated from their domains, never scanned from localStorage.
6. **Retire legacy keys per domain** only after that domain reports `cutover`, keeping rollback
   available until the workflow is verified in both hosts.

### 21.6 What this does not decide

It does not schedule the work, and it does not change any code today. It fixes the owner so the
next slice has one answer: settings first (no migration), then characters (needs a store), then
worlds/scenarios (store exists, bindings missing), then the two cache-only splits.

### 21.7 Settings authority inversion — landed (`5f32dd5`)

The settings cutover (§21.5 item 1) is complete. `runtime.Settings` is the only
authority; `settings-state.js` is the only renderer module that talks to it.

**Load.** `GetSettings` is asked first on every load, including when it returns
an empty document (a fresh install is authoritative, not a reason to fall back).
The document is merged over defaults in memory. The cache is consulted only when
the binding is missing or throws, and only when it carries
`{version: 2, savedAt, settings}`. A legacy raw object, a truncated envelope or a
cache from another schema is ignored and rendered over defaults. `source`
reports `backend`, `cache` or `defaults` so the outcome is inspectable. After an
authoritative read the cache is rewritten from the backend document, which is
the rebuild path for an empty, stale or conflicting cache.

**Write.** `set(path, value)` builds a snapshot, sends the whole document to
`SetSettings`, and only after the acknowledgement updates `current` and writes
the versioned cache. Saves are serialized (last-write-wins) so two rapid writes
cannot land out of order. A rejected write reverts `current` to the last
acknowledged document, leaves the cache byte-identical, and emits
`howl:settings-write-failed`. The form bindings that mutate `current` as a draft
still call `saveSettings()`, which uses the same backend-first path. The explicit
`flushSettings()` rejects on failure, so the audio page's "Saved" state cannot
claim a write that did not reach disk.

**One seam.** `sampler-settings.js`, `model-settings.js`, `chat-think.js` and
`image-generator-core.js` no longer call `SetSamplerSettings`, `SetModelOptions`
or mutate `current` behind the seam; they use `settingsState.set/get`.
`GetSettings` now returns the document plus the live sampler and model sections,
so no renderer page needs the legacy per-section getters. `menu-view.js` reads
scale/animation only from the snapshot and re-applies on
`howl:settings-loaded`; `character/world/scenario/lorebooks/story-tools/index`
load `settings-state.js` so every window has the same authority.

**UI-only split.** `ui-prefs.js` owns the `howl-ui:` namespace and is documented
as renderer-only; the settings modal's last panel is its first user. The legacy
`howl-chat-ui-scale` and `howl-chat-animation-speed` keys are no longer read and
are cleared by the wipe.

**Renderer.** The repository reads the backend first, imports a pre-cutover

`{version: 3, ui: {currentMode, seedLocked, aspectLocked}}`. Generation values
live in `howl-image-generation-cache`, written only after an acknowledged
backend read or save. Saves are serialized, merge against the acknowledged
projection, and change the projection/revision/cache only after the binding
returns; a refused save leaves all three untouched so a retry cites the same
valid revision. `restoreState` awaits repository readiness before applying
values, and `loadModels` restores the saved model without re-running the family
preset over the restored generation values. No other renderer module reads or
writes either generation key through `localStorage`; the static renderer test
enforces that.

**Evidence.** `internal/image/settings/settings_test.go` covers create, stale
refusal, merge preservation, legacy revision derivation, and engine-save
preservation. `app-image-generation_test.go` covers the bindings and one-time
import. `tests/renderer/image-generation-repository.test.js` proves
backend-over-cache, one-time legacy import reduced to UI state, save ordering
(no projection or cache change during the binding call), refused-save revision
retention and successful retry, cleared-cache reload from the backend, failed
import preservation, and no direct generation-key access outside the
repository. A clean checkout of the amended commit with an empty initial
`git status --short` passes `go build ./...` (0), `go vet ./...` (0), the full
`go test ./... -skip TestProbeMicrophoneOnHost -count=1` suite (0), and 33
renderer tests (0). The pass found and fixed one real ordering defect before
the final commit: `save()` initially re-ran the backend load after readiness,

### 21.11 Chat session pointer — landed

HOC §21.5 item 5 is complete. `howl-chat-current-session` is now a version-2
pointer owned by `chat-session-pointer.js`; it carries the active chat id and
the UI selection only, and hydration resolves full records from the domain
repositories.

**Before.** `context-data.js` read the key as a session-shaped blob and, when
loading it, scanned `howl-chat-lorebooks` directly to rebuild lorebooks.
`sidebar-session.js` and `data-sync.js` wrote and removed the same key in
several places. The stored blob could contain whole world, scenario, character
and lorebook records, which duplicated the catalogs and let a stale cache
outlive a repository update.

**Pointer shape.** The module writes
`{version: 2, chatId, selection: {worldId, scenarioId, characters, lorebookIds,
activeCharacterIds, removedCharacterIds, addedCharacterIds, activeLorebookIds,
removedLorebookIds, addedLorebookIds}}`. A character entry in `characters` is
`{id}` plus only the UI fields `status`, `active`, `stepOutReason` and
`stepOutMode` when present. No names, descriptions, images, prompts or other
catalog records are written. The chat id comes from the canonical bridge state
first, then `dataSync.currentChatId`, then the sidebar session.

**Hydration.** `hydrate()` awaits `WorldRepository`, `ScenarioRepository`,
`CharacterStorage`/`CharacterRepository` and `LorebookRepo`, finds records by
the stored ids, and merges the stored character UI fields over the canonical
record. `LorebookRepo` is now loaded on the chat page and gained an `all()`
projection. `loadChatDataFromStorage` uses `read()` and `hydrate()`; a legacy
session blob is converted to the id-only shape once and kept only in memory as
a first-hydration fallback, then rewritten as a pointer. No pointer flow reads
the raw lorebook catalog from `localStorage`.

**One owner.** `context-data.js` delegates every write to
`ChatSessionPointer.write`. `sidebar-session.js` writes after a session load and
after chat-data cache saves, and uses `clear()` on new-chat/load/delete paths.
`data-sync.js` uses `clear()` for its reset paths. `app-wipe.js` still names the
key because a full application reset must remove it; it does not write catalog
state. A static renderer check rejects any other module naming the key.

**Evidence.** `tests/renderer/chat-session-pointer.test.js` (6 tests) proves the
written envelope contains no catalog text, hydration resolves names from fake
repositories while preserving selection fields, a legacy blob migrates once and
loses its embedded records, a raw lorebook catalog is not used, the chat id
prefers the bridge, `clear()` removes only the pointer, and no module outside
the owner and wipe names the key. Full renderer suite and Go gates are recorded
in checkpoint 102.

**User-visible evidence.** In the browser dev host on `127.0.0.1:8799` with an
isolated OS-temp root, a fresh chat wrote a v2 pointer with an empty selection;
selecting the fixture world, scenario and character wrote
`worldId: "item5-world"`, `scenarioId: "item5-scenario"` and
`characters: [{id: "item5-character"}]` with no catalog names in the raw value
(under 400 bytes). Hydrating that live pointer returned the canonical fixture
titles from the repositories, and reloading restored all three in the UI. The
packaged WebView2 host was also driven: after selecting the same three fixtures,
the WebView2 Local Storage record contained only the chat id and ids, and
closing/reopening the app restored the world, scenario and character panels.

**Left open in this area.** Other context-entry paths that add lorebooks still
read the pre-cutover lorebook cache directly, because only `LorebookRepo`
reports cutover. §21.5 item 6 remains dependent on per-domain cutover markers;
the pointer itself no longer duplicates any catalog.
