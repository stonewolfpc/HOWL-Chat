## 2. Finding — identity comparison alone accepted a junction escape (F-A1)

The owner asked whether identity-based containment "remains correct across volume boundaries, symlinks,
junctions, and race conditions". **It did not.** The first implementation resolved each path's identity and walked
lexical ancestors upward looking for the root's identity. Against a real junction it returned **contained** for a
path that physically lives outside the root:

```
root\esc        → junction →  outside
candidate        = root\esc\secret\file.txt     (physically outside\secret\file.txt)
first implementation verdict: CONTAINED          ← wrong
```

The walk from `root\esc\secret` reaches `root` — a genuine lexical parent whose identity matches — without ever
crossing the junction's target. Lexical ancestry and physical ancestry diverge at a reparse point, and the
identity test followed the lexical one.

**Why the test existed.** The limitation was reported honestly in the task record ("no real junction created") and
the audit's first act was to create one. Junction creation does not require elevation (`mklink /J`), so the
limitation was closable rather than inherent. **The failing test is the audit's most important product.**

### Correction

Containment now resolves **physical** paths before comparing:

1. Resolve the existing prefix to its canonical physical path, re-append the not-yet-created remainder
   (`physicalPath`).
2. Compare the two physical paths by components (`containsPath`), which is now sound because both sides are real.
3. **Fail closed** if either side cannot be resolved to a physical path (ADR-001 §7 doctrine).

Volume serial and file index remain the basis for volume-level comparison and are still used by the cross-volume
test, but they are no longer the containment test.

### A second, independent trap found while fixing it

`filepath.EvalSymlinks` **does not resolve junctions on this toolchain** (go1.27.3 windows/amd64). The first
correction attempt used it and the test still failed. Physical resolution therefore uses
`GetFinalPathNameByHandle` with `FILE_FLAG_BACKUP_SEMANTICS`, stripping the `\\?\` prefix. Recorded as **I-09**:
any future path code in this repository that relies on `EvalSymlinks` will silently fail to follow a junction.

| **Race conditions (TOCTOU)** | **NOT closed, and not claimed** | `CheckContained` is a pre-flight check. A reparse point created after it returns is not detected. ADR-001 §7 requires handle-relative writes for the guarantee; that is contract F work, not TASK-01 |

Verbatim-position note: the function's doc comment now states the TOCTOU boundary explicitly rather than leaving
it to inference.

### 3.2 External-resource grants — classification vs authorization vs capability

| Concept | Where it lives | What it does |
|---|---|---|
| **Classification** | `ExternalRoot()` → `Root{Writable: false}` | Says what the location *is*. Never writable |
| **Authorization** | `CheckGrant()` | Tests whether a candidate is strictly inside a granted operation subtree; refuses the destination root itself |
| **Write capability** | **Does not exist** | No grant store, no handle-relative writer. That is `ExternalDataGuard` + contract F |

**Verdict: not conflated, because the third thing is absent rather than approximated.** The residual risk is a
caller reading `Writable: true` on a *content* root as permission to write anywhere inside it. That risk is real
but is not a path-service defect: `Writable` describes the root, not the operation. Recorded as condition **C-1**
for `TASK-02`.

`TestExternalRootIsReadOnlyAndNeverGrants` and `TestCheckGrantRequiresStrictlyInside` — **PASS**.

### 3.3 Writerless resolution

The owner's point was correct and the audit found the defect was **in my own comment**, not only in the code.
`Roots()` was documented as performing "no filesystem creation". That is false in isolation mode: `ResolveIsolation`
→ `newIsolation` calls `MkdirAll` for `data`, `temp`, `webview2` and `data/config`.

- **Correction applied:** the comment now states the installed-mode guarantee and names the isolation exception as
  I-02.
- **Behaviour pinned:** `TestIsolationResolutionCreatesLayoutOnce` asserts the layout is absent before the first
  resolution, present after it, and unchanged by repeated resolutions — **PASS**. Changing it now requires
  deliberately changing that test.
- **Not fixed:** making resolution truly writerless would change established isolation behaviour, which is outside
  TASK-01's authorized scope. Carried to the call-site migration task.

|---|---|---|
| Three separate launches resolve identically | proven by `chdir` in one process | **Demonstrated literally:** a built probe executed as three separate processes from the repository root, `%TEMP%`, and `D:\` produced **byte-identical** stdout (`diff` clean, twice) |

## 6. Decision

**TASK-01 is accepted as complete for its bounded contract**, having passed its acceptance criteria and having had
one genuine defect found and corrected during audit.

Three conditions carry forward, none of which blocks closure:

- **C-1** `Writable` is a classification, never an authorization. `TASK-02` must not read it as permission.
- **C-2** Any write path must use handle-relative operations to obtain the TOCTOU guarantee that
  `CheckContained` deliberately does not provide.
- **C-3** `I-09` stands: do not use `filepath.EvalSymlinks` for containment anywhere in this repository.

`TASK-01` is **closed**. `TASK-02` — DurableStore — is **not started**, per the owner's instruction that the audit
is the branch boundary.
