## 1. What this contract replaces, and why

**RC-01 — The retired question.** The 528–546 series asked whether an exact filesystem identity could be *proved* destroyed. Six investigations established that it cannot: absence by open-by-ID is indeterminate (1h, 542), attribution is unavailable (1h U-11), USN evidence needs elevation (546). Every one of those conclusions stands.

**RC-02 — The question that replaces it.** Whether a conversation's data is still *available*. This is answerable without privilege, and it is the only question the interface needs answered.

**RC-03 — The two are not the same claim, and no field in this contract implies the other.** Nothing here asserts authorship, destruction, or cooperation from the filesystem. There is **no deletion receipt** in this model.

**RC-04 — Rows 528–546 are preserved unedited.** They are a complete record of a harder problem that is no longer being solved. Later readers must not treat them as current policy, and must not treat them as mistaken.

## 2. Storage contract this rests on

**RC-05 — Where a conversation lives (Source-derived: `internal/backend/chat/persistence.go`).**

```
<rootDir>/chats/<chatID>/
    meta.json          always written on save            (persistence.go:204)
    history.ndjson     true source of truth, append log  (persistence.go:586-698)
    history.json       legacy, migrated into ndjson      (persistence.go:211, 673)
    world.json         written only when non-empty       (persistence.go:217)
    scenario.json      written only when non-empty       (persistence.go:224)
    characters.json    always written                    (persistence.go:230)
    lorebooks.json     written on save                   (persistence.go:235)
    memories.json      written on save                   (persistence.go:240)
```

Plus optional memory-subsystem files written by other packages (`auto_capture_config.json`, `memories_backup.json`, `continuity_config.json`, `candidates.json` — Source-derived).

**RC-06 — The manifest is generated from this contract, never from disk.** For each conversation a manifest records the paths that *must* exist for it to be healthy, generated at creation from the storage contract version in force. It is **never** derived by scanning what happens to be present.

**RC-07 — Why that rule matters.** A damaged conversation would otherwise redefine its own requirements: delete `history.ndjson`, rescan, and the file is no longer "expected", so the conversation looks healthy. The manifest must be immune to the state it is measuring.

**RC-08 — Manifest shape.**

| Field | Meaning |
|---|---|
| `contract_version` | which storage layout generated this manifest |
| `required` | paths that must exist |
| `alternatives` | groups where at least one member must exist (`history.ndjson` or legacy `history.json`) |
| `optional` | paths that may exist; absence never affects state |

**RC-09 — Minimum content.** `meta.json` is always required. Content requires at least one member of the history alternatives group. Files this contract does not list are **not required** (RC-08 `optional`), so a future feature cannot silently make old conversations damaged.

**RC-10 — Legacy conversations.** A conversation created before manifests existed has none. Until one is generated by migration from its `contract_version`, its state is **Unavailable** (RC-14), never Healthy. Migration generates manifests from the storage contract; it does not read the directory to decide what to require.

## 3. States

**RC-11 — Six states, all derived from observation.** No state is a stored claim; each is recomputed from the manifest and the latest observation. The worklist records *intent to reconcile*, never an outcome.

| State | Definition | UI behaviour |
|---|---|---|
| **Healthy** | every `required` path exists, and every `alternatives` group has ≥1 member | normal conversation |
| **Pending reconciliation** | a worklist entry exists and no successful observation has been made since | normal, with an unobtrusive marker if desired |
| **Missing** | the conversation directory itself does not exist, or **all** required content is absent | removed from the active list and index |
| **Damaged** | some required data exists and some is absent — including a failed `alternatives` group | shown as damaged; never as normal; never auto-repaired |
| **Unavailable** | the scan could not establish the condition (denied, I/O error, incomplete listing, manifest missing) | retained, marked as unresolved, retried |
| **Orphaned** | a directory exists on disk with no corresponding index entry | reported for diagnosis; **never** imported or deleted automatically |

**RC-12 — Forbidden transitions.**

| From | To | Why |
|---|---|---|
| Unavailable | Healthy | an error is not evidence of health |
| Unavailable | Missing | an error is not evidence of absence |
| Damaged | Missing | partial evidence is not total absence, and deleting the index entry would discard the remaining data's owner |
| Damaged | Healthy | only a new observation with all requirements met may say Healthy |
| Orphaned | Healthy | requires a user decision, not a scan |
| any | (automatic repair) | the scanner never writes to conversation data (RC-16) |

**RC-13 — Damaged is the state a failed deletion produces.** A partly-successful removal leaves some paths gone and others present. It must be visible, because silently keeping it presents a broken conversation as healthy, and silently removing it discards the user's remaining data.

## 4. Scan

**RC-14 — Read-only by construction.** The scanner opens, stats and lists. It **never** deletes, creates, repairs, moves, renames or imports. Any future need to act on a conversation is a separate, user-initiated operation.

**RC-15 — Outcome table.** One observation, mapped against the manifest:

| Observation | State |
|---|---|
| all `required` present, each `alternatives` group satisfied | Healthy |
| conversation directory absent | Missing |
| directory present, no content at all | Missing |
| directory present, `meta.json` present, content partly present | Damaged |
| `meta.json` present, `alternatives` group unsatisfied but other required present | Damaged |
| listing incomplete, or any path denied / errored | **Unavailable** |
| manifest absent or unreadable | **Unavailable** |
| directory found during full sweep, no index entry | Orphaned |

**RC-16 — A scan error never becomes Missing, and Unavailable never becomes Healthy.** Both directions are forbidden in RC-12 and are acceptance-tested (RT-03, RT-04).

**RC-17 — Incomplete enumeration is an error, not evidence.** A listing that stops early (E/A, I/O error, timeout) yields Unavailable for that conversation. The count of what was seen is not used to infer what is absent.

## 5. Deletion flow and the worklist

**RC-18 — The flow.**

1. the user deletes a conversation;
2. Howl writes a **worklist entry** naming the conversation;
3. Howl performs its ordinary automated removal of `<rootDir>/chats/<chatID>/`;
4. a scan observes the result and the index is reconciled (RC-11);
5. the worklist entry is retired once a scan has resolved that conversation.

**RC-19 — Ordering is a speed decision, not a correctness one.** Because the worklist is not authority (RC-21), an entry written before removal is harmless if removal never happens: the scan observes the directory still present and the conversation stays Healthy. Equally, a lost entry is harmless because the full sweep rediscovers the condition. This is the property that makes the design robust without a journal.

**RC-20 — The worklist is not a receipt.** It carries no outcome, no authorship, no hash, no timestamp claim about success. Writing it says only "look at this conversation soon".

**RC-21 — The worklist is an optimization; the full sweep is the authority.**

| Mechanism | Role |
|---|---|
| worklist scan | fast path for known deletion/reconciliation requests |
| full sweep | compares the conversation index against on-disk directories; catches lost entries, failed worklist writes, and conditions created while Howl was closed |

**RC-22 — Orphans are reported, never adopted.** A directory with no index entry is surfaced for diagnosis. Automatic import would resurrect data the user believed deleted; automatic deletion would destroy data Howl does not own. Both are prohibited.

**RC-23 — Deletion scope.** Ordinary removal targets exactly the conversation's own directory. It must be confined to the resolved `<rootDir>/chats/<chatID>` subtree: never a parent, never a path assembled from user input without containment checking, never a path that resolves outside `chats/`. This is a weaker rule than the retired D-10 and is the only identity rule this contract keeps — it constrains what may be deleted, not what may be claimed.

## 6. Cadence

**RC-24 — Startup plus periodic, bounded.** Startup catches everything that happened while Howl was closed; periodic catches deletions during a long session, which startup-only would leave stale until relaunch.

| Trigger | Purpose |
|---|---|
| startup | reconcile after time closed |
| periodic, fixed interval with jitter | reconcile the current session |
| resume from sleep | timers are unreliable across suspend |
| manual refresh | user-initiated, bypasses the interval |

**RC-25 — Bounded work.** Each pass has a record cap and a time budget, so a large worklist cannot stall startup or flood I/O. Unprocessed entries carry to the next pass.

**RC-26 — Retry with backoff, and a persistent attempt counter.** An entry whose scan errors is retried with increasing delay for that record alone. Without the counter a permanently denied path retries forever at full rate. The counter is diagnostic only; it never changes the state to Missing.

**RC-27 — Concurrent instances.** Jitter (RC-24) reduces synchronized passes. The contract does not require coordination between instances; every state is derived from observation, so a redundant scan is harmless.

## 7. What is explicitly not claimed

| Claim | Status |
|---|---|
| "Howl deleted this" | not claimed anywhere; authorship is unestablishable (542) |
| "The data is destroyed" | not claimed; only that required paths are not currently available |
| "The filesystem cooperated" | not claimed |
| "Physical identity was verified" | retired with the identity-proof series |
| Anything requiring elevation or USN | out of scope; 546 shows both are unavailable unelevated |

**RC-28 — Wording rule.** No user-facing string may render Damaged, Missing or Unavailable as a deletion confirmation. "Deleted" describes the user's intent; the observed condition is "no longer available", "partly unavailable", or "could not be determined".

## 8. Acceptance tests

- **RT-01** Healthy requires every `required` path and every `alternatives` group satisfied.
- **RT-02** Directory absent → Missing; removed from index and active list.
- **RT-03** Denied path → Unavailable, never Missing.
- **RT-04** Unavailable is never reported as Healthy without a new successful observation.
- **RT-05** `history.ndjson` removed while `meta.json` and others remain → **Damaged**, not Healthy, not Missing.
- **RT-06** Alternatives group unsatisfied (`history.ndjson` and `history.json` both absent) → Damaged.
- **RT-07** Manifest generated at creation is unaffected by files deleted afterwards (no self-redefinition, RC-07).
- **RT-08** Legacy conversation with no manifest → Unavailable until migration generates one.
- **RT-09** Scanner performs zero writes to conversation data (syscall-level assertion, not code review).
- **RT-10** Deletion whose worklist write is lost is still reconciled by the full sweep.
- **RT-11** Deletion that never happened leaves the conversation Healthy even though an entry exists.
- **RT-12** Orphaned directory is reported and neither imported nor deleted.
- **RT-13** Incomplete enumeration yields Unavailable, never a partial Missing/Damaged inference.
- **RT-14** Attempt counter grows on repeated errors and does not change state.
- **RT-15** No user-facing string claims deletion confirmation (string-table lint).
- **RT-16** Deletion of a path outside `<rootDir>/chats/<chatID>` is refused.
