## 1. Writer lock lifecycle — **sound**

| Question | Answer, and its evidence |
|---|---|
| Acquisition | `acquireLock` opens `<doc>.lock` and requests `LockFileEx` **exclusive**, byte range `[0,1)`, `FAIL_IMMEDIATELY`, polled every 25 ms until `LockTimeout` (5 s default). No other path writes the document |
| Ownership | Per open handle, enforced by the kernel. `Save` acquires it **before any mutation** — before the temp sweep, staging, manifest commit and rename — and releases via `defer` on every return path |
| Release | `UnlockFileEx` + `Close` in `release()`. `release` also nil-guards, so a double release cannot panic |
| Process termination | **Measured, three ways** (probe output in §5) |
| Failure to acquire | Returns `Busy` with `lock_not_acquired_within_<duration>`; `TestSaveReportsBusyWhenLockHeld` additionally asserts the document is unchanged |
| Stale lock | **Cannot occur.** A surviving lock *file* is not a held lock: Windows releases byte-range locks when the owning process dies, and the file itself carries no state. No code path deletes the lock file — deleting it is the only way to manufacture a double-writer hole, and that is deliberately impossible |

Measured sequence, using an independent probe binary against the same lock file:

| Step | Result |
|---|---|
| A — probe while another **live process** holds the lock | `blocked (The process cannot access the file because another process has locked a portion of the file.)` |
| B — that process exits normally; lock file still on disk; probe again | `acquired` |
| C — a process dies **mid-commit** (`os.Exit(9)` inside `Save`, lock held) | exit code `9` |
| D — probe after that death | `acquired` |
| E — directory afterwards | lock file and manifest remain; no temp, no staged generation |

So a crashed writer cannot wedge the application, and a leftover lock file cannot admit a second writer.
**Residual, not a defect:** there is no lease or expiry. A *hung* (not dead) process holding the lock produces
`Busy`, which is the required D4 behaviour rather than a bypass.

## 2. Commit and recovery protocol — **one defect found and corrected**

### 2.1 Ordering as delivered

```
lock → sweep dead temps/staged → temp write, Sync, close
     → rotate pre-images (OVERWRITES v1..vN) → manifest commit → [injection point]
     → rename temp→live (3 × 50 ms) → trim beyond N → release
```

### 2.2 Defect F-A2 — a failed commit destroyed the newest retained generation

Rotation ran **before** the rename and wrote directly over `v1`…`vN`. When replacement was denied by a reader,
`restoreManifest` put back a manifest whose recorded hashes no longer matched the rewritten files: `v1` now held the
current live document while the manifest still said it held the previous one. The chain and its manifest were
desynchronized, and the newest real generation became unreachable.

Reproduced before the fix, with a plain sequence — three commits, one reader-induced failed commit, then
corruption:

```
audit_test.go:44: after failed commit, v1 = "d3", want the untouched d2
```

Follow-on effect: `Load` on a corrupt document then reported `corrupt_no_valid_preimage` — **recovery failed after a
routine reader-contention event**, on a chain that had been intact seconds earlier. This blocks acceptance
criterion A-7 and falsifies the record's claim that "a failed commit never rotates".

**Correction.** Pre-images are now *staged* beside their final names and promoted only after the live rename
succeeds; a failed commit aborts the staging and touches nothing retained:

```
lock → sweep → temp write, Sync, close → stage v1..vN as *.staged
     → manifest commit → [injection point] → rename temp→live
     → promote staged → trim beyond N → release
```

`TestFailedCommitPreservesPreImageChain` and `TestFailedCommitLeavesNoStagedArtifacts` now pass. Also corrected in
the task record: the ordering description, and the defect count (two → three).

### 2.3 Interruption points: tested versus reasoned

| Point | Tested? | State after | Recovery observes |
|---|---|---|---|
| After temp write, before staging | **No** — reasoned | live untouched, no staged files | live matches manifest → `Saved`; leftover temp swept next write |
| After staging, before manifest | **No** — reasoned | live untouched, staged files orphaned | `Saved`; staged swept under the next lock |
| After manifest, before rename | **Yes** — `TestCrashBeforeReplaceLeavesPreviousDocument` (real process death) | live = previous; manifest = new intent | `Recovered(interrupted_commit_rolled_back)`; **previous document returned** |
| After rename, before promote | **No** — reasoned | live = new; manifest = new; retained files = old generation | `Saved`; a later corruption may fall back one generation older |
| During promote | **No** — reasoned | partially promoted chain | `Saved`; recovery skips generations whose hash does not match |
| After rename, before trim | **No** — reasoned | live = new; one extra retained generation | `Saved`; trimmed next write |

**One injection point is tested; the rest are source-derived.** The injected point is the one where a real
alternation of committed state exists (intent recorded, replacement not done). The others leave the live document
either untouched or already correct, which is why they are reasoned rather than injected — but they are not
measured, and the record says so.

### 2.4 What recovery actually restores

`Load` restores **a complete, hash-verified generation** — never partial bytes, never an empty document. It picks
the newest pre-image whose bytes hash to the value the manifest recorded. If none matches it returns
`NotSaved(corrupt_no_valid_preimage)` rather than guessing.

## 3. Reader consistency — **sound, with one stated degradation**

| Question | Answer |
|---|---|
| Is the pair coherent? | `Load` reads live + manifest and re-reads **both** up to 3 times (2 ms apart) whenever the hash does not match. Because the manifest is committed *before* the rename, a committed pair can only mismatch transiently |
| Under repeated concurrent commits | `TestReaderNeverObservesPartialDocument`: 20 commits against continuous reads, five runs (3 plain, 2 under `-race`); every successful read returned exactly the old or the new document |
| When retries are exhausted | Three distinct outcomes, all complete documents: `Recovered(interrupted_commit_rolled_back)` if the live bytes equal a retained generation; `Recovered(from pre-image)` if some pre-image matches; `NotSaved(corrupt_no_valid_preimage)` otherwise. **Torn bytes are never returned** |
| Degradation | Under continuous commits faster than the retry window, a reader can return the **previous** generation marked `Recovered` while a newer one is landing — one generation behind, never mixed. Not measured under sustained load; stated, not claimed |
| Reader's effect on writers | A reader holds the document only for one open/read/close; a reader that holds longer causes `NotSaved(rename_denied_by_open_reader)`, never a forced write |

## 4. Acceptance evidence — what is proven, and what the two skips mean

| Claim | Proven by | Nature of the evidence |
|---|---|---|
| Process-crash leaves the previous document readable | `TestCrashBeforeReplaceLeavesPreviousDocument` | **Real OS process death.** A separate process (`exec.Command`) runs `Save`, hits the injection point and calls `os.Exit(9)`; the parent observes exit code 9. The *timing* is injected; the *death* is real |
| Cross-process single-writer | `TestBusyAcrossProcesses` + the probe sequence in §1 | Real second process holding a real kernel lock |
| The lock is released by process death | probe steps C–D; and implicitly the crash test's later successful `Save` | Measured |
| Rotation/recovery/schema/reader-denial/round-trip | 11 further tests | Direct |

**The two helper skips are not missing coverage.** `TestCrashChildDurable` and `TestLockHolderChild` are entry points
driven through `DURABLE_*` environment variables; in a normal run they skip in the parent, and they execute fully
inside the child process. Driven manually they were observed to exit `9` (crash child) and `0` (lock holder). A skip
here means "runs in a child", not "does not run".

**Process crash ≠ power loss.** Process death loses no flushed bytes and the rename is already on the volume.
Power-loss durability remains **`UN`**: `Sync` ordering exists, NTFS metadata durability for the rename itself is not
demonstrated, and no claim of it is made.
