## Store boundary

`internal/worldstore` remains the only writer of canonical world/scenario item folders.

- `StageImport` validates the destination category, save and write roles, availability, identity shape, envelope, allowlisted lore names, sizes, optional media JSON, and ownership marker. It writes under
  `<root>/.howl-import-staging/<operationID>/<itemID>/`; the owner marker is
  `<itemID>.owner.json` beside that folder, so it can never be published into the canonical item.
- `CommitImport` takes the existing process-wide `writeMu`. Under that lock it re-reads the destination registration, requires the same root and save+write roles, calls `Lookup` across all registered roots, requires a complete and non-indeterminate search, re-verifies every staged hash, requires the final path absent, and only then renames staging into `<root>/<id>/`. It never replaces an existing final path.
- `AbortImport` takes `writeMu`, verifies the owner marker and the exact staged document/lore/media set, and refuses if the final path exists or any unexpected file is present. It never deletes unexpected files or another operation's staging.
- `LoadStaging` reconstructs a staged item from its owner marker for explicit resume; it verifies the marker and every staged hash.
- `VerifyImported` proves an existing canonical item still has the journaled revision and every journaled document/lore/media hash. It changes nothing.
- `RemoveImported` is used only by explicit rollback. It requires the journaled revision, verifies every expected file hash, rejects missing files and unexpected files/directories/symlinks, and then removes the item folder.
- Staging is under the same destination root as the final folder, so the commit rename is same-filesystem. The first staging segment is not a valid item ID, and `Lookup` only reads `<root>/<id>/world.json` or `scenario.json`; staging is not discoverable as an item.

No import path calls `library.Registry.WriteFile` or `WriteNewFile` for world/scenario content.

## Execution and plan authority

- `Preview` is purely observational. It creates no directory, journal, marker, staging file, or temp file, and writes no source content to logs.
- `Execute` re-runs preflight from the original request and compares the re-derived plan hash. A changed source, destination registration, role, authority result, or existing destination item returns `plan_stale`; the renderer's plan object is never a write authorization.
- The plan hash covers category, destination ID/root/status, conversion version, errors, every source fingerprint, proposed identity, disposition/reason, document/lore/media hashes, reference issues, and intended write set.
- Known reference fields are normalized losslessly to typed references; unknown fields and per-reference extras survive. ID-only resolution remains the runtime rule.
- Adoption requires document, lore, and normalized media equality. A missing/present or differing media manifest is `media_conflict`.
- Absent, empty, and whitespace-only lore owners are stamped with the mapped item ID; foreign owners remain `unmapped_owner` and are never rewritten.
- Atomicity is per item. A multi-item operation can end `completed_partial`; it never claims transaction-wide atomicity.
- Journal and marker files live under the app configuration directory, not under content roots. The journal mutex only protects that metadata file; canonical writes are authorized by the store's `writeMu`.

## Crash/recovery matrix

The service journal records per-item `planned`, `prepared`, `committed`, `adopted`, `quarantined`, `rolled_back`, `failed`, `ambiguous`, `cleanup_failed`, and `cleanup_complete` states.

| Boundary | Durable evidence | Recovery decision | Test |
|---|---|---|---|
| After operation journal, before staging | `planned`, no staging, no final | Mark `failed`; no content change; operation completes partially | `after_journal` |
| After complete staging, before `prepared` journal | `planned`, complete staging with owner marker | Verify owner marker and staged hashes, then commit | `after_stage` |
| During staging / incomplete staging | `planned`, staging exists but hashes do not verify | `ambiguous`; do not delete or commit | `TestIncompleteStagingRequiresExplicitAmbiguity` |
| After `prepared` journal, before commit | `prepared`, staging present, final absent | Revalidate authority, verify staged hashes, commit | `after_prepared` |
| After rename, before `committed` journal | `prepared`, final present, staging absent | Verify recorded final hashes and record `committed`; never infer that the rename failed | `after_rename` |
| After `committed` journal, before marker | `committed`, final present | Verify hashes; complete the operation and marker | `after_committed` |
| After completion marker | terminal operation and marker | No-op; item remains unchanged | `TestCompletedMarkerResumeIsNoOp` |
| Final path without verifiable journal hashes | incomplete evidence | `ambiguous`; no deletion or overwrite | `TestIncompleteStagingRequiresExplicitAmbiguity` path |

Source hashes are captured before each crash and rollback test and compared afterward. No recovery path writes, renames, or deletes a source folder. Browser records remain caller-owned memory; the Go service never reads or writes `localStorage`.

## Outcomes and quarantine reasons

Implemented explicit outcomes include:

- `ready`, `adopt` with no writes, `completed`, `completed_partial`, `resume_required`, `plan_stale`, `operation_active`, `already_imported`.
- `adopted`, `committed`, `quarantined`, `failed`, `ambiguous`, and `rolled_back` per item.
- Reasons: `missing_document_id`, `invalid_document_id`, `duplicate_identity`, `duplicate_name`, `identity_conflict`, `lore_conflict`, `media_conflict`, `unmapped_owner`, `unsupported_source_file`, `unsupported_media_manifest`, `inline_media_unmigrated`, `destination_unavailable`, `destination_not_rollback_safe`, `authority_indeterminate`, `source_destination_overlap`, `source_registered`, `cleanup_failed`, `ambiguous_state`, and `write_failed`.

Exact-ID matching is the only automatic identity evidence. Titles and folder names are display data only. Explicit user resolutions can map to an existing identity or request a store-generated new identity; the resolution evidence and actor are carried into the journal. Inline browser media is quarantined, never dropped or written; legacy `media.json` is copied only when it is reference-only. Unsupported legacy files quarantine their folder rather than being skipped silently.

## Rollback proof

Rollback is two-phase:

1. Verify the whole operation first: every committed item must match its journaled revision and document/lore/media hashes; no unexpected files; no adopted item; no ambiguous item; no prepared item with a final path; no owned staging or owner marker left by a committed item.
2. Only then remove verified, journal-created items through `worldstore.RemoveImported` under `writeMu`, and remove verified failed/quarantined staging through `AbortImport`. Adopted items, sources, and browser records are never deleted or rewritten.
3. A failed cleanup or surviving marker keeps the operation `rollback_partial` with `cleanup_failed`; it is never reported as `rolled_back`.

Tests cover a later lore edit (refused, item retained), an adopted item (rollback refused), a clean import (removed and marker cleared), source-tree byte equality before/after, unexpected staging files, abort/commit concurrency, and a rollback that refuses to delete an unexpected file. A later document edit is covered by the same revision/hash verification path. Cleanup failures are reported, not hidden.

## Deviations and limitations

- **Reference normalization is lossless but intentional.** Known fields receive typed references and unknown fields/extras survive; unknown-kind and kind-mismatch entries are preserved but not resolved at runtime. `legacyName` is migration/display evidence only.
- **Commit cleanup remains best-effort after a successful rename.** `CommitImport` removes the owner marker and empty staging directories after the rename; `Rollback` now refuses to report `rolled_back` if that evidence remains. This is visible rather than destructive.
- **Media bytes are not migrated.** Only reference-only manifests are accepted; inline payloads quarantine the source. F3-F remains out of scope.
- **No fsync/power-loss guarantee.** Fault injection simulates process termination at service boundaries, not disk-cache loss or OS crash. Cross-process writers remain outside the desktop single-process contract.
- **Root-level files in a legacy source root** are reported as plan errors, while unsupported files inside a candidate item folder quarantine that folder as `unsupported_source_file`. Both are explicit; neither is silently imported.
- `Resume` and `Rollback` require explicit user/API calls. There is no automatic startup recovery.
- Journal listing is read-only and per category; no UI consumes it yet.
- The import page and native acceptance remain unimplemented by design.

### Failure behavior before and after

- A completed journal with no marker previously resumed from the journal. It now returns `integrity_failure`; the canonical item remains loadable and unchanged.
- A malformed, stale, contradictory, or foreign marker previously had no read/compare path. It now blocks `Execute`, `Resume`, and `Rollback` with explicit evidence; a foreign marker is preserved.
- A `cleanup_failed` item previously actioned as quarantine while contributing zero to `Plan.Quarantined`. It now contributes one; mixed cleanup produces `Quarantined=2`, `Conflicted=0`, and operation status `ambiguous`.
- A prepared item whose staging was removed during rollback was recorded as `cleanup_complete` and could be counted as quarantined on a later `Resume`. It is now `rolled_back`; `cleanup_complete` remains limited to cleaned failed/quarantined dispositions.
- Malformed media previously reported `unsupported_media_manifest`. It now reports `malformed_media_manifest`; structurally valid unsupported media keeps `unsupported_media_manifest`. Neither path writes media bytes.
- Reference edge cases are now preserved and classified without a name fallback; lossless update/reload retains unknown per-reference fields. Production runtime resolution remains an explicit boundary because no consumer exists in this slice.
